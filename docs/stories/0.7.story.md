## Story

**As a** cliente do app Keepit,
**I want** acompanhar meu pedido do aceite até a entrega — incluindo o PIN de retirada e as telas de exceção (cancelamento, lojista não veio) — e consultar meu histórico em "Meus pedidos",
**so that** eu saiba exatamente em que fase o pedido está, consiga confirmar a retirada com segurança e tenha acesso ao meu histórico de compras, tudo sem depender de nenhum backend real (Épico 0 é 100% mock).

## Acceptance Criteria

1. Telas implementadas com fidelidade visual ao protótipo: Confirmar retirada / PIN, "Cheguei ao hub", Recibo / pedido concluído, Meus pedidos (em andamento / histórico), telas de exceção (cancelar, "lojista não veio").
2. Transições de estado do pedido (`Novo → Aceito → Em preparo → Saindo para o hub → No hub → Entregue` + ramos `Cancelado` / `Não retirado`) mockadas em memória via `order.port`.
3. Estados loading / vazio / erro fiéis (exercitados via injeção de latência/erro do mock).
4. Fidelidade visual verificada contra o protótipo `keepit-app/index.html`.

### Máquina de estados do pedido (fonte de verdade)

Estados oficiais definidos na decisão de negócio (Rodada 2) e refletidos no schema real de `pedidos.status`:

**Caminho feliz:** `Novo → Aceito → Em preparo → Saindo para o hub → No hub → Entregue`
[Source: docs/PERGUNTAS_REGRAS_NEGOCIO.md#Rodada 2 — Fluxo do pedido — modelo iFood-like — "[Estados do pedido]"]

**Enum real no banco (`pedidos.status`)** — usar estes valores como base para os nomes internos do mock, já que a port "espelha o schema real" por decisão arquitetural do épico:
```
aguardando_pagamento, aguardando_aceite, aceito, em_preparo, saindo_hub, no_hub,
entregue, cancelado, cancelado_timeout, cancelado_atraso, cancelado_admin,
recusado, nao_retirado, nao_entregue_lojista, estornado_chargeback
```
[Source: docs/architecture/03-data-models.md#5.1 `pedidos`]

**Nota de mapeamento**: o épico usa nomenclatura amigável em português ("Novo", "Aceito", "Em preparo"...) para as ACs, enquanto o schema real usa `aguardando_aceite`, `aceito`, `em_preparo`. O mock (Story 0.2) deve usar os valores do enum real (para não divergir do schema quando plugar Supabase no Épico 1); a UI desta story traduz para os rótulos amigáveis apenas na exibição. Não inventar um terceiro conjunto de nomes.

**Gatilhos e regras de tempo relevantes a esta story:**
- O gatilho de "Saindo para o hub" é o **lojista** marcando no app dele — o cliente só recebe a atualização de status (mock) e um push (mock/visual) para ir ao hub.
- Após ambos (cliente e lojista) marcarem "Cheguei ao hub", há **janela de 10 min de tolerância** para o encontro se concretizar.
- Confirmação da entrega: cliente **mostra** o PIN de 4 dígitos; é o **lojista** quem digita o PIN no app dele (Story 0.10, fora desta story) — nesta story (Cliente), o PIN é apenas **exibido**, nunca digitado pelo cliente.
- [Source: docs/PERGUNTAS_REGRAS_NEGOCIO.md#Rodada 2]

### Matriz de cancelamento e reembolso (decidida — Rodada 2, sujeita a validação final do stakeholder)

Todos os percentuais/prazos abaixo **DEVEM vir de `packages/config`** — nenhum hardcode na tela, mesmo sendo texto informativo:

| Situação | Resultado |
|---|---|
| Cliente cancela antes do aceite | 100% reembolso |
| Timeout de aceite do lojista (10 min) | Cancelamento automático + 100% reembolso |
| Cliente cancela após aceite, antes de "Saindo para o hub" | 90% reembolso ao cliente / 10% fica com o lojista |
| Cliente cancela após "Saindo para o hub" | **Não pode cancelar** — precisa comparecer ou perder |
| Cliente não apareceu (10 min pós-chegada do lojista) | 20% reembolso ao cliente / 80% para o lojista (ação do lojista, não do cliente) |
| Lojista não apareceu no hub | Cliente aciona "Lojista não veio" → 100% reembolso + registro de falha de qualidade do lojista |
| Atraso do lojista (2x tempo estimado sem marcar "Saindo para o hub") | Cliente recebe opção "Aguardar mais" ou "Cancelar com 100% reembolso" |

[Source: docs/PERGUNTAS_REGRAS_NEGOCIO.md#Rodada 2 — Cancelamento e exceções]

**Execução do reembolso é sempre manual** (admin dispara estorno via Asaas) — isso é 100% fora do escopo desta story (Épico 0 é mock); a tela do cliente apenas comunica o resultado esperado, sem processar reembolso real. [Source: docs/PERGUNTAS_REGRAS_NEGOCIO.md#Rodada 6 — "[Reembolso — execução]"]

**PIN — regras relevantes (para copy/contexto, não para lógica de validação nesta story, já que quem digita é o lojista):**
- PIN de 4 dígitos.
- 5 tentativas para o lojista digitar; após esgotar, bloqueia 5 min e libera automaticamente.
- Não existe fallback de reenvio de PIN pelo cliente — se perder acesso, aciona suporte via WhatsApp (fora do escopo de tela desta story, mas relevante se a UI mencionar isso em algum texto de ajuda).
[Source: docs/PERGUNTAS_REGRAS_NEGOCIO.md#Rodada 6]
