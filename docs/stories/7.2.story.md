## Reconciliação com o épico (escopo e path)

- **O épico assume "Edge Function `criar-pedido` (do Épico 6)"** — mas o
  Épico 6 foi implementado como **RPC Postgres** (`criar_pedido` /
  `criar_pedido_com_ledger`, `SECURITY DEFINER`), não como Edge Function.
  Não existe nenhuma Edge Function `criar-pedido` para "integrar". Esta
  Story reconcilia criando uma **Edge Function nova e separada**,
  `create-pix-payment`, chamada pelo client (`Pagamento.tsx`, modo
  supabase) **depois** que `order.create` (RPC `criar_pedido`) já criou o
  pedido — não uma integração dentro da RPC. Isso preserva a
  atomicidade/transação da RPC (que já grava PIN, itens e snapshot
  financeiro) e evita reabri-la para chamar uma API HTTP externa de dentro
  de uma transação SQL (Postgres não faz `fetch`).
- **Decisão de sequência — DEFAULT de status (AC1).** A migration
  `20260813004932_criar_pedidos.sql` deixou o `DEFAULT` de
  `pedidos.status` como `'aguardando_aceite'` (pagamento simulado, dev) —
  o modelo-alvo do §5.1 é `'aguardando_pagamento'`. Confirmado por leitura
  direta das duas RPCs ativas
  (`20260813004934_rpc_criar_pedido.sql` linha 176 e
  `20260813050002_rpc_criar_pedido_com_ledger.sql` linha 122): **ambas
  gravam o status explicitamente na lista de colunas do `INSERT`**
  (`'aguardando_aceite'`), nunca dependendo do `DEFAULT` da tabela. Logo:
  - Esta Story **flipa o `DEFAULT` da coluna** para `'aguardando_pagamento'`
    (alinha com o modelo-alvo do §5.1) — mudança **sem nenhum efeito
    comportamental hoje**, porque nenhuma RPC ativa depende do `DEFAULT`
    (todo `INSERT` já lista `status` explicitamente).
  - Esta Story **NÃO edita as RPCs `criar_pedido`/`criar_pedido_com_ledger`**
    para passarem a gravar `'aguardando_pagamento'`. Fazer isso agora
    prenderia todo pedido novo em `aguardando_pagamento` para sempre — a
    Story 7.5 (webhook `PAYMENT_RECEIVED`) é quem promove
    `aguardando_pagamento → aguardando_aceite`, e ela **não existe ainda**.
    Mudar a RPC nesta Story, sem o webhook, criaria exatamente os "pedidos
    presos" que a missão instruiu evitar.
  - O que esta Story entrega em paralelo: depois que o pedido já nasce
    (via RPC, continua indo direto a `aguardando_aceite`, comportamento
    hoje inalterado), o client (modo supabase) chama a nova Edge Function
    `create-pix-payment` para criar a cobrança PIX real no Asaas e
    persistir `asaas_payment_id`/`qr_code_pix`/`pix_copia_e_cola` no
    mesmo pedido — em paralelo ao ciclo de vida simulado, sem bloqueá-lo.
  - **[AUTO-DECISION]** Sequência de ativação → flipar o `DEFAULT` agora
    (inofensivo, já alinhado ao modelo-alvo) + construir toda a
    infraestrutura de cobrança real (Edge Function, `PaymentPort`) nesta
    Story, mas **deixar para a Story 7.5** (ou uma story de "religamento"
    dedicada, quando o webhook existir) a mudança que faria o pedido
    **de fato nascer bloqueado em `aguardando_pagamento`** até a
    confirmação real chegar. (reason: evita pedidos travados sem nenhum
    caminho de confirmação — exatamente o risco que a missão pediu para
    evitar; a infraestrutura fica pronta e testada, só o "gate" de verdade
    liga depois.)
  - Consequência prática para o QA/Dev desta Story: **não há regressão de
    UX** — o cliente continua vendo o mesmo fluxo (`ModalPagamentoPix` com
    QR **FAKE** de `pixCopiaCola`, confirmação simulada em ~5s,
    `ModalConfirmarPin` na sequência). O que muda é que, em paralelo (modo
    supabase), uma cobrança PIX **real** passa a existir no Asaas sandbox
    para aquele pedido — auditável, mas ainda não exibida/consumida pela
    UI (ver "Fora de escopo" abaixo).
- **Fecha CARRY-001 da Story 7.1**: a derivação segura de base URL
  (sandbox por default, produção só com `ASAAS_ENVIRONMENT === 'production'`,
  override explícito por `ASAAS_BASE_URL`) é implementada e testada nesta
  Story, no entrypoint da Edge Function `create-pix-payment` — ver AC2.
- **Fora de escopo desta Story (explícito, não é lacuna esquecida):**
  - Trocar o QR **exibido** em `ModalPagamentoPix` pelo QR **real** do
    Asaas (`qr_code_pix`/`pix_copia_e_cola` persistidos). A tela continua
    usando `pixCopiaCola(pedido)` (100% fake, client-side) nos dois
    `DATA_SOURCE` — trocar a fonte de dados da UI implicaria também repensar
    o timer de confirmação automática de ~5s (`usePagamentoSimulado`), que
    é incompatível com uma cobrança PIX real (que só confirma quando
    alguém escaneia e paga de verdade, evento tratado pela 7.5). Deferido
    para quando o webhook (7.5) e a decisão de UX de "aguardar pagamento
    real" existirem.
  - Editar `criar_pedido`/`criar_pedido_com_ledger` para gravar
    `'aguardando_pagamento'` (ver decisão de sequência acima).
  - Cartão (Stories 7.3/7.4) e webhook (Story 7.5/7.11) — não tocados.
  - Reuso de `asaas_customer_id` por cliente entre pedidos diferentes: a
    tabela `clientes` não tem (e esta Story não adiciona) uma coluna para
    guardar o id do customer Asaas. Cada chamada a `create-pix-payment`
    chama `criarCliente` de novo (idempotência só existe **por pedido**,
    via `asaas_payment_id` já gravado — ver AC4). Isso pode criar
    múltiplos customers Asaas para o mesmo cliente Keepit ao longo de
    vários pedidos — aceitável no piloto (conta sandbox, baixo volume,
    sem custo/limite relevante disso); dedup por cliente fica para uma
    story futura se o piloto pedir.

## Story

**As a** sistema,
**I want** gerar uma cobrança PIX real no Asaas (com QR Code) assim que um
pedido é criado,
**so that** exista um registro de cobrança real e auditável no gateway de
pagamento para aquele pedido, pronto para a Story 7.5 confirmar via
webhook.

## Acceptance Criteria

1. Migration `apps/supabase/supabase/migrations/{timestamp}_pedidos_add_asaas_pix.sql`
   adiciona a `pedidos`: `asaas_payment_id text UNIQUE`, `qr_code_pix text`,
   `pix_copia_e_cola text` (as 3 colunas nullable, sem `NOT NULL` — nem
   todo pedido terá cobrança Asaas, ex. pedidos de teste/mock antigos) +
   índice `idx_pedidos_asaas ON pedidos(asaas_payment_id) WHERE
   asaas_payment_id IS NOT NULL`. A migration também troca o `DEFAULT` da
   coluna `status` de `'aguardando_aceite'` para `'aguardando_pagamento'`
   — mudança **sem efeito comportamental** hoje (nenhuma RPC ativa depende
   do `DEFAULT`; ambas gravam `status` explicitamente no `INSERT`, ver
   "Decisão de sequência" acima). A migration documenta em comentário SQL
   por que o flip é seguro e o que falta para ele "valer" de fato (Story
   7.5 + edição futura das RPCs). Nenhuma RLS nova é necessária: a Edge
   Function grava essas 3 colunas via client com a `service_role` key
   (bypassa RLS, mesmo padrão de toda RPC `SECURITY DEFINER` do projeto).
2. **(Fecha CARRY-001 da Story 7.1.)** Uma função pura e testável (ex.:
   `apps/supabase/supabase/functions/create-pix-payment/config.ts`,
   `resolveAsaasConfig(env)`) resolve `{ baseUrl, apiKey }` a partir de um
   objeto `{ get(key: string): string | undefined }` injetado (nunca
   `Deno.env` direto — só o entrypoint `index.ts` faz essa ponte). Regras:
   se `ASAAS_BASE_URL` estiver setada (não vazia após `trim()`), ela
   **sempre** vence, sem barra final; senão, deriva de
   `ASAAS_ENVIRONMENT`: `=== 'production'` → `https://api.asaas.com/v3`;
   **qualquer outro valor, incluindo ausente/vazio/desconhecido** →
   `https://api-sandbox.asaas.com/v3` (default seguro — nunca produção por
   omissão). Testes cobrem os 4 casos (ausente, sandbox explícito,
   production, `ASAAS_BASE_URL` sobrepondo `production`) + trim de espaços
   + barra final. `apiKey` vem de `ASAAS_API_KEY` (string vazia se
   ausente — o teste de `criarCliente` no handler cobre o caso de a
   chamada ao Asaas falhar com chave vazia, não é responsabilidade desta
   função validar a chave).
3. `PaymentPort` (`packages/core-data/src/ports/payment.port.ts`) expõe
   `criarCobrancaPix(pedidoId: string, options?: AsyncCallOptions):
   Promise<PixChargeResult>`, com `PixChargeResult = { pedido_id: string;
   asaas_payment_id: string; qr_code_pix: string; pix_copia_e_cola: string
   }`. Dois adapters:
   - **Mock** (`packages/core-data/src/mock/payment.mock.ts`): gera um QR
     fake determinístico a partir do `pedidoId` (mesma família de ideia de
     `apps/cliente/src/lib/pagamentoSimulado.ts#pixCopiaCola`, reimplementada
     localmente em `core-data` — **não** importada de `apps/cliente`, que
     é um app consumidor, nunca uma dependência de um package — ver Dev
     Notes) e simula a persistência via um `Map` interno ao closure do
     adapter (idempotente: 2ª chamada para o mesmo `pedidoId` retorna o
     mesmo resultado, sem "recriar"). Nunca lança para `pedidoId`
     desconhecido — lança um erro descritivo `[mock]`, mesmo padrão de
     `order.mock.ts`.
   - **Supabase** (`packages/core-data/src/supabase/payment.supabase.ts`):
     chama `supabase.functions.invoke('create-pix-payment', { body: {
     pedido_id: pedidoId } })` — **primeira chamada a `functions.invoke`
     no repositório** (nenhum precedente — ver Dev Notes para os detalhes
     de tratamento de erro do supabase-js). Em caso de `error` (rede/HTTP
     não-2xx) ou `data` no formato de erro (`{ error: {...} }`), lança um
     `Error` com mensagem legível; em sucesso, retorna o `PixChargeResult`
     do corpo da resposta.
4. Edge Function `apps/supabase/supabase/functions/create-pix-payment/`:
   - `handler.ts` exporta uma função pura `handleCreatePixPayment(input,
     deps)` — **nunca importa `Deno`**. `deps` injeta `asaasClient:
     AsaasClient` (de `_shared/asaas.ts`) e um repositório mínimo
     `pedidos: { getById(pedidoId): Promise<PedidoParaCobranca | null>;
     salvarCobrancaPix(pedidoId, fields): Promise<void> }` (interface
     própria deste módulo, não o tipo `SupabaseClient` — mantém o handler
     100% testável sob Vitest, mesmo padrão de `fetchImpl` injetado da
     Story 7.1). Fluxo: busca o pedido (404 `PEDIDO_NAO_ENCONTRADO` se não
     achar); **idempotência** — se o pedido já tem `asaas_payment_id` +
     `qr_code_pix` + `pix_copia_e_cola` preenchidos, retorna esses valores
     direto, **sem chamar `asaasClient`** (testável com um `asaasClient`
     fake que falha o teste se qualquer método for chamado); senão chama
     `criarCliente` (nome/CPF do cliente do pedido; erro `CLIENTE_SEM_CPF`
     se `cliente_cpf` vier nulo — defensivo, não deveria acontecer dado o
     gate de checkout, ver Dependencies) → `criarCobranca` (`billingType:
     'PIX'`, `value = total_pago_reais`, `dueDate` = hoje via `deps.now()`
     injetável, `externalReference = pedido.id`) → `obterQrCodePix` →
     `pedidos.salvarCobrancaPix(...)` → retorna `{ asaas_payment_id,
     qr_code_pix, pix_copia_e_cola }`. Qualquer etapa do Asaas que falhe
     (`ok: false`) propaga um erro tipado (`status`/`code`/`message` do
     `AsaasError` correspondente), sem continuar as etapas seguintes.
   - `index.ts` é o entrypoint `Deno.serve` — lê o body JSON (`{
     pedido_id }`), monta `resolveAsaasConfig({ get: (k) =>
     Deno.env.get(k) })` (AC2), cria `createAsaasClient(config)` (Story
     7.1) e um client Supabase real com a `service_role` key (bypassa RLS
     — mesmo padrão de toda escrita privilegiada do projeto), implementa o
     repositório `pedidos` contra as tabelas reais (`pedidos` join
     `clientes` para nome/CPF), chama `handleCreatePixPayment`, e traduz o
     resultado em uma resposta HTTP (`200` + corpo em sucesso; `404/422/502`
     conforme o erro em falha). **Este arquivo usa `Deno.serve`/
     `Deno.env` e por isso não é (nem pode ser) exercitado por Vitest** —
     só `handler.ts`/`config.ts` são testados diretamente; `index.ts` é
     fino o bastante (monta deps reais, chama o handler puro, traduz o
     resultado) para que revisão manual + os testes do handler cubram a
     lógica de fato.
   - Como `index.ts` usa `Deno.serve`/`Deno.env.get`, que não existem no
     `lib` do TypeScript configurado para Node (`apps/supabase/tsconfig.json`
     → `tsconfig.base.json`, sem `Deno` declarado — mesma lacuna que a
     Story 7.1 evitou tocando em `Deno` só no comentário), este arquivo
     precisa de uma declaração ambiente mínima para não quebrar `tsc
     --noEmit`. **[AUTO-DECISION]** Criar
     `apps/supabase/supabase/functions/_shared/deno-globals.d.ts` com uma
     declaração `declare const Deno: { serve(handler: (req: Request) =>
     Response | Promise<Response>): void; env: { get(key: string): string
     | undefined } }` — subset mínimo usado pelo entrypoint, reutilizável
     pelas Edge Functions futuras (7.5/7.11). (reason: mesma decisão de
     arquitetura da 7.1 — `pnpm qa`/`tsc --noEmit` sob Node precisa
     typechecar sem o binário `deno` instalado; isso não afeta o runtime
     real do Deno, que tem seus próprios globals mais completos — a
     declaração local só serve o `tsc` do monorepo.) Se `deno` estiver
     disponível no ambiente de execução, `deno check`/`deno test` também
     devem funcionar sobre este código sem alterações (mesma nota
     TEST-001 herdada da 7.1).
5. `Pagamento.tsx` (`apps/cliente/src/screens/home/Pagamento.tsx`), dentro
   de `handlePagar`: depois que `client.order.create(...)` resolve com
   sucesso e **só quando `isSupabaseDataSource()`**
   (`apps/cliente/src/lib/dataSource.ts`, mesmo helper já usado em outras
   telas — ver Dev Notes), chama `await client.payment.criarCobrancaPix(pedido.id)`
   **best-effort**: se falhar, captura o erro, **não** bloqueia nem
   propaga para o `catch` existente de `handlePagar` (não introduz um
   novo estado de erro visível ao cliente) — só um `console.warn`/log —
   e o fluxo continua exatamente como hoje (navega para
   `ModalPagamentoPix`/`ModalProcessandoPagamento`). Em modo mock,
   `handlePagar` **não muda nenhuma linha de comportamento observável**
   (chamar ou não `client.payment.criarCobrancaPix` no mock é indiferente
   ao usuário, já que o mock não altera nenhum outro estado visível — a
   Story pode optar por chamá-lo também em mock por paridade de código ou
   restringir ao `isSupabaseDataSource()`; qualquer uma das duas é
   aceitável desde que documentada, mas a restrição a supabase é o desenho
   recomendado por ser mais simples de revisar). `ModalPagamentoPix`
   continua usando `pixCopiaCola(pedido)` (fake) para o QR exibido — ver
   "Fora de escopo".
6. Testes vitest cobrindo: `config.ts` (AC2, 4+ casos), `handler.ts` (AC4:
   caminho feliz completo, idempotência sem tocar `asaasClient`, cada
   etapa do Asaas falhando isoladamente, `cliente_cpf` nulo), `payment.mock.ts`
   (determinismo + idempotência), `payment.supabase.ts` (sucesso e os 2
   formatos de erro do `functions.invoke`). `pnpm qa` na raiz do monorepo
   permanece 100% verde (inclui `apps/supabase` e `packages/core-data`).

## Dev Notes

### Por que uma Edge Function separada, não dentro da RPC `criar_pedido`

RPCs Postgres não conseguem fazer chamadas HTTP de dentro da transação
(sem uma extensão tipo `pg_net`, que não está em uso no projeto). O épico
descreve "Edge Function `criar-pedido` (do Épico 6) integrada com Asaas",
mas o Épico 6 real é uma RPC. `create-pix-payment` é chamada pelo client
**depois** que a RPC já criou o pedido — mesmo padrão de "efeito colateral
pós-criação" já usado por `confirmarPagamento` (Story 6.7.1), só que agora
com uma chamada de rede real em vez de um no-op.
[Fonte: `apps/supabase/supabase/migrations/20260813004934_rpc_criar_pedido.sql`,
`20260813050002_rpc_criar_pedido_com_ledger.sql` — ambas sem nenhuma
chamada HTTP; `docs/prd/epics/7-pagamento-carteira.md` Story 7.2 AC1]

### `resolveAsaasConfig` — fechando CARRY-001 (AC2)

```ts
// apps/supabase/supabase/functions/create-pix-payment/config.ts
export interface EnvReader { get(key: string): string | undefined; }
export interface ResolvedAsaasConfig { baseUrl: string; apiKey: string; }

export function resolveAsaasConfig(env: EnvReader): ResolvedAsaasConfig {
  const apiKey = env.get('ASAAS_API_KEY') ?? '';
  const explicitBaseUrl = env.get('ASAAS_BASE_URL')?.trim();
  if (explicitBaseUrl) {
    return { baseUrl: explicitBaseUrl.replace(/\/+$/, ''), apiKey };
  }
  const environment = env.get('ASAAS_ENVIRONMENT')?.trim();
  const baseUrl = environment === 'production'
    ? 'https://api.asaas.com/v3'
    : 'https://api-sandbox.asaas.com/v3'; // default seguro — nunca produção por omissão
  return { baseUrl, apiKey };
}
```

`index.ts` chama `resolveAsaasConfig({ get: (k) => Deno.env.get(k) })` —
é a ÚNICA ponte com `Deno.env` de toda a Story. Testes injetam um `Map`
ou objeto literal como `EnvReader`, sem nenhuma dependência de `Deno`.

### `handler.ts` — contrato de dependências (AC4)

```ts
// apps/supabase/supabase/functions/create-pix-payment/handler.ts
import type { AsaasClient } from '../_shared/asaas';

export interface PedidoParaCobranca {
  id: string;
  cliente_nome: string;
  cliente_cpf: string | null;
  total_pago_reais: number;
  asaas_payment_id: string | null;
  qr_code_pix: string | null;
  pix_copia_e_cola: string | null;
}

export interface PedidosRepo {
  getById(pedidoId: string): Promise<PedidoParaCobranca | null>;
  salvarCobrancaPix(pedidoId: string, fields: {
    asaas_payment_id: string; qr_code_pix: string; pix_copia_e_cola: string;
  }): Promise<void>;
}

export interface CreatePixPaymentDeps {
  asaasClient: AsaasClient;
  pedidos: PedidosRepo;
  now?: () => Date; // injetável para teste; default = () => new Date()
}

export type CreatePixPaymentResult =
  | { ok: true; data: { asaas_payment_id: string; qr_code_pix: string; pix_copia_e_cola: string } }
  | { ok: false; error: { status: number; code: string; message: string } };

export async function handleCreatePixPayment(
  input: { pedido_id: string },
  deps: CreatePixPaymentDeps,
): Promise<CreatePixPaymentResult>;
```

`PedidosRepo` é uma interface própria deste módulo — **não** o tipo
`SupabaseClient` do `@supabase/supabase-js` (que não é dependência de
`apps/supabase`, ver `package.json`). Isso mantém `handler.test.ts`
livre de qualquer setup de Supabase real, mesmo padrão de `fetchImpl`
injetado da Story 7.1 (`asaas.test.ts`). `index.ts` é quem implementa
`PedidosRepo` de verdade, contra as tabelas `pedidos`/`clientes` via
`@supabase/supabase-js` com a `service_role` key (que a Edge Function já
tem acesso via `Deno.env.get('SUPABASE_SERVICE_ROLE_KEY')`, padrão-padrão
de toda Edge Function Supabase — não é uma env var nova desta Story).

**Idempotência (AC4):** se `getById` retornar um pedido com as 3 colunas
já preenchidas, o handler retorna esses valores **sem chamar
`asaasClient`** — testável com um `asaasClient` fake cujos métodos lançam
se forem chamados (mesmo padrão `fetchThatFailsIfCalled` da
`asaas.test.ts`, Story 7.1).

**`dueDate`:** usar a data de hoje (`deps.now()`, formatada `YYYY-MM-DD`)
— não é uma regra de negócio (prazo de pagamento), é só o campo obrigatório
do Asaas para o dia em que a cobrança PIX passa a ser válida; PIX é
"aprovação na hora" (`SelectableRow` em `Pagamento.tsx`, highlight
existente), então hoje é o valor correto e não precisa de configuração.

**CPF nulo defensivo:** `cliente_cpf` não deveria vir nulo (gate de
checkout, Story 6.5), mas o handler trata esse caso com um erro nomeado
(`CLIENTE_SEM_CPF`, `status: 422`) em vez de deixar `criarCliente` falhar
de forma opaca no Asaas — é uma validação de fronteira, não uma nova regra
de negócio.

### `payment.supabase.ts` — primeira chamada a `functions.invoke` do repo

Nenhum adapter existente usa `supabase.functions.invoke` (confirmado por
busca no repositório) — é território novo. Formato do supabase-js v2:
`const { data, error } = await supabase.functions.invoke<T>('nome', {
body })`. `error` cobre falha de rede/transporte e respostas HTTP não-2xx
(`FunctionsHttpError`/`FunctionsRelayError`/`FunctionsFetchError`); quando
`error` existe, `data` normalmente é `null`. O adapter deve tratar os dois
casos (mesmo padrão de outros adapters supabase do projeto, que lançam
`Error` com mensagem legível em vez de propagar o objeto de erro cru do
SDK — ver `order.supabase.ts` linha ~511 para o estilo).
