## Story

**As a** dev solo,
**I want** promover para `packages/core-data` (+ `packages/config`) os métodos que hoje vivem como adaptadores locais em `apps/cliente`, `apps/lojista` e `apps/admin`, e religar os hooks/contexts dos apps para consumir as ports promovidas,
**so that** a fronteira mock→Supabase volte a ser única e completa antes do Épico 1 plugar o backend real, sem nenhuma tela precisar ser reescrita quando a fonte de dados mudar de mock para Supabase.

## Acceptance Criteria

1. `OrderPort` (`packages/core-data/src/ports/order.port.ts`) ganha o **lado lojista**: `listByEstabelecimento(estabelecimentoId, options?)`, `markReadyForHub(pedidoId, options?)`, `markArrivedAtHub(pedidoId, options?)`, `markCustomerNoShow(pedidoId, motivo, options?)` — mesmos nomes e assinaturas já usados no adaptador local `apps/lojista/src/screens/pedidos/lojistaOrders.mock.ts` (Story 0.10). `apps/lojista/src/screens/pedidos/OrdersContext.tsx` passa a consumir exclusivamente `client.order` (via `getDataClient()`); `lojistaOrders.mock.ts` é removido.
2. `OrderPort` ganha o **lado cliente**: `getById(pedidoId, options?)` e uma forma real de avançar o pedido pelos estados que hoje não têm método (`em_preparo`, `saindo_hub`, `no_hub`) e de registrar `cliente_chegou_em` — nome do(s) método(s) a critério do @dev (ex.: `advanceStatus`/`markClienteChegou`), documentado na Dev Notes. `apps/cliente/src/context/OrderStatusOverrideContext.tsx` é removido; as telas que o consomem (`OrderStatusDevAdvancer`, `ModalConfirmarPin`, etc.) passam a chamar `client.order` diretamente.
3. `AuthPort` (`packages/core-data/src/ports/auth.port.ts`) ganha `getById(clienteId, options?)` (resolve `Cliente` a partir do id — usado pelo Lojista para exibir nome/telefone do cliente num pedido) e `updateCpf(clienteId, cpf, options?)` (coleta de CPF no 1º checkout, Story 0.6). `CLIENTE_NOME_POR_ID`/`nomeClienteDisplay` (hoje hard-coded em `lojistaOrders.mock.ts`) são removidos em favor de `client.auth.getById(pedido.cliente_id)`. O gap 10.4 (modelo de auth do Cliente — telefone/SMS vs. e-mail/senha) **não é resolvido nesta story**: fica registrado como dependência do stakeholder em `docs/PERGUNTAS_REGRAS_NEGOCIO.md` seção 10, e `AuthPort` continua modelando apenas `nome`+`telefone` (sem introduzir e-mail/senha sem decisão fechada).
4. `AdminPort` (`packages/core-data/src/ports/admin.port.ts`) ganha os métodos hoje só em `apps/admin/src/mock/adminOpsMock.ts`: `listClientes(filtros?, options?)`, `blockCliente(clienteId, motivo, options?)`, `unblockCliente(clienteId, options?)`, `suspendLojista(estabelecimentoId, motivo, options?)`, `financialDashboard(periodoDias, options?)`, `lojistaQualityView(estabelecimentoId, options?)`, uma listagem administrativa de pedidos com filtro opcional de status (nome a critério do @dev, ex.: `listAllOrders(filtros?, options?)`) e `forceCancelOrder(pedidoId, motivo, options?)`. `refundQueue` deixa de começar sempre vazia: **toda transição para um status de cancelamento/recusa/no-show** (`order.cancel`, `forceCancelOrder`, futuro timeout) passa a inserir a entrada correspondente em `db.reembolsos` (mesma lógica hoje só em `forceCancelOrder` do mock local do Admin), com o `motivo` correto do enum `ReembolsoMotivo`. `apps/admin/src/mock/adminOpsTypes.ts`, `adminOpsFixtures.ts`, `adminOpsMock.ts` e `asyncOpsHelpers.ts` são removidos; as telas do Admin passam a consumir `client.admin`/`client.order`.
5. `ProductPort` (`packages/core-data/src/ports/product.port.ts`) ganha `delete(id, options?)` (soft delete via `excluido_em`, nunca remove a linha) e o método `update()` existente passa a aceitar o campo `ativo` (permitindo reativar um produto pausado, não só pausar via `pause()`). `list()` ganha um parâmetro opcional (ex.: `incluirInativos?: boolean`) para a tela "Gerenciar catálogo" poder listar produtos pausados/excluídos quando necessário. `apps/lojista/src/screens/catalogo/ProductCatalogContext.tsx` remove as mutações "local-only" (comentários `TECH DEBT` em `toggleAtivo`/`deleteProduto`) e passa a refletir o retorno real de `client.product.update`/`client.product.delete`.
6. `StorePort` (`packages/core-data/src/ports/store.port.ts`) ganha um método de escrita `setPausadoManualmente(estabelecimentoId, pausado, options?)`. `apps/lojista/src/screens/catalogo/LojaDisponibilidadeContext.tsx` remove o comentário `TECH DEBT` de "estado local-only" e persiste o toggle "recebendo pedidos" via `client.store.setPausadoManualmente`, sobrevivendo a um novo `getById`.
7. As agregações financeiras do Lojista hoje em `apps/lojista/src/screens/financeiro/financeiro.mock.ts` (vendas por período 7d/30d/90d/1a, top produtos, extrato mensal) são promovidas para `packages/core-data`, derivadas de `db.pedidos`/`db.pedidos_itens` reais (não mais fixtures estáticas desconectadas do mock db). O @dev decide e documenta explicitamente: **(a)** estender `WalletPort` com esses métodos, ou **(b)** criar um novo `analytics.port.ts` — em ambos os casos, a decisão preserva o limite deliberado de "poucas ports" do Épico 0 e é justificada na Dev Notes (REUSE > ADAPT > CREATE, conforme `.claude/rules/ids-principles.md`). `financeiro.mock.ts` é removido; as telas de Financeiro passam a consumir a port promovida.
8. O carrinho + cartão salvo do Cliente (`apps/cliente/src/context/CartContext.tsx`) é **avaliado explicitamente** pelo @dev: decisão de (a) criar uma port nova (`cart.port`) cobrindo `carrinho`/`carrinho_itens`/`clientes_cartoes`, ou (b) manter o carrinho como estado client-side local (justificando por que "carrinho" é legitimamente efêmero/rascunho, diferente das demais ports que representam dados persistidos), documentada na Dev Notes com prós/contras. Se a decisão for (a), implementar `cart.port` seguindo o mesmo padrão das demais; se for (b), nenhuma mudança de código é exigida neste item além de registrar a decisão e remover o comentário `[TECH DEBT]` do arquivo trocando-o por uma nota de decisão definitiva (não mais pendência).
9. `packages/config` (`businessConfig`) ganha os percentuais de reembolso da matriz de cancelamento fechada na Rodada 2 (`docs/PERGUNTAS_REGRAS_NEGOCIO.md`): cancelamento antes do aceite (100%), cancelamento após aceite antes de "Saindo para o hub" (90% cliente / 10% lojista), cliente não apareceu no hub (20% cliente / 80% lojista), lojista não apareceu no hub (100% cliente). `apps/cliente/src/lib/cancelamentoPolicy.ts` deixa de hard-codar esses valores localmente e passa a reexportar/derivar de `businessConfig` (mantendo `cancelamentoFaseFromStatus` como helper local, pois é lógica de derivação de UI, não um valor de regra).
10. Nenhuma tela de nenhum dos 3 apps foi alterada visualmente (mesmo layout, mesmos textos, mesma navegação) — esta é uma story de refactor de camada de dados, não de UI. `pnpm turbo run typecheck`, `pnpm turbo run lint` e `pnpm turbo run test` passam sem regressão nos workspaces já existentes, e os testes de contrato novos (Vitest) cobrem cada método promovido (shape de retorno, assincronicidade real, `forceError`/`forceEmpty` onde aplicável). Um `grep` final confirma que nenhum arquivo `*.mock.ts` local de app (fora de `packages/core-data`) e nenhum comentário `[TECH DEBT]` referente aos gaps desta story permanece em `apps/*`.

### Matriz de cancelamento — valores exatos para `businessConfig` (AC9)

Fonte: `docs/PERGUNTAS_REGRAS_NEGOCIO.md` linhas 358-364 (Decisões → Rodada 2 → Cancelamento e exceções):
