## Story

**As a** lojista,
**I want** ver meu extrato financeiro real (vendas e saques do mês),
**so that** eu tenha visão confiável do meu financeiro sem depender de
dado mockado.

## Acceptance Criteria

1. `AnalyticsPort.monthlyStatement` no adapter Supabase (hoje
   `NotImplementedError`) retorna, para o mês corrente (UTC), a união de:
   (a) pedidos `status = 'entregue'` do estabelecimento com `entregue_em`
   dentro do mês corrente, mapeados para `tipo: 'venda'`, `valorReais =
   subtotal_produtos_reais - taxa_keepit_reais + taxa_deslocamento_reais`,
   `taxaKeepitReais = taxa_keepit_reais`, `descricao = 'Venda #{numero}'`;
   (b) lançamentos `lancamentos_financeiros` tipo `payout`,
   `status <> 'erro'`, do estabelecimento, com `criado_em` dentro do mês
   corrente, mapeados para `tipo: 'saque'`, `valorReais =
   ABS(valor_centavos)/100`, `descricao = 'Saque · PIX'`.
2. Resultado ordenado do mais recente para o mais antigo (`data DESC`),
   igual ao mock.
3. RLS já garante isolamento por `estabelecimento_id` — o adapter não
   reimplementa checagem de ownership além de filtrar pelo
   `estabelecimento_id` recebido.
4. Tela "Extrato" (já existente) continua funcionando sem alteração de
   código — resumo "Repasse líquido"/"Recebido"/"Taxas Keepit" (calculado
   em `financeiroPresentation.ts` a partir do array retornado) reflete
   dados reais.
5. Mês sem nenhuma movimentação retorna array vazio (estado "Nenhuma
   movimentação neste mês" já tratado pela tela, sem mudança).
6. Testes cobrem: mês com vendas e saques misturados (ordenação
   correta); mês vazio; `taxaKeepitReais` presente só em `tipo: 'venda'`;
   isolamento entre dois estabelecimentos; paridade de fórmula com
   `analytics.mock.ts#monthlyStatement` para o mesmo conjunto de dados de
   teste.

## Dev Notes

### Contexto e limites

- Esta Story **não toca UI** — `ExtratoFinanceiro.tsx` e
  `financeiroPresentation.ts` já existem e já chamam
  `client.analytics.monthlyStatement`.
- **Por que a "venda" vem de `pedidos`, não do ledger**: o `AnalyticsPort`
  foi desenhado deliberadamente como um READ MODEL separado de
  `WalletPort` (ver cabeçalho de `analytics.port.ts`, decisão [IDS] da
  Story 1.10) — agregações de vendas/produtos vêm de
  `pedidos`/`pedidos_itens`, não da carteira. Isso é coerente mesmo após
  a unificação do ledger (Story 7.6): o valor líquido de uma venda
  (`subtotal - taxa_keepit + deslocamento`) pode ser calculado
  diretamente do snapshot em `pedidos` sem depender de o `merchant_credit`
  já ter sido lançado no ledger — ambos devem bater porque usam a mesma
  fórmula (Story 7.12), mas a fonte de leitura desta Story é `pedidos`,
  não o ledger. Só a parte "saque" desta Story lê o ledger
  (`lancamentos_financeiros` tipo `payout`, já que não existe mais tabela
  `saques` própria no piloto — ver Story 7.6/7.7).

### Fórmula de referência (paridade obrigatória com o mock)

```
venda.valorReais = subtotal_produtos_reais - taxa_keepit_reais + taxa_deslocamento_reais
venda.taxaKeepitReais = taxa_keepit_reais
saque.valorReais = ABS(lancamentos_financeiros.valor_centavos) / 100.0
```
