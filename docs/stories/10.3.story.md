## Data Mode

- Modo: **mock**. Seed vive exclusivamente em `createMockDb()`
  (`packages/core-data/src/mock/db.ts`) — a mesma função que já semeia
  `clientesCredenciaisFixture` (Cliente) e `saquesFixture`. `createMockDb()`
  só é chamado por `createDataClient({ source: 'mock' })`; no build
  `production` (`EXPO_PUBLIC_DATA_SOURCE=supabase`) ela **nunca** é
  instanciada — os adapters Supabase reais são usados no lugar. O seed desta
  story é, portanto, estruturalmente inacessível a `source: 'supabase'`.
- Compatibilidade: mudança **aditiva** aos dois arrays (`db.lojistaContas`,
  `db.estabelecimentosCadastrados`) que hoje nascem `[]`. Não altera nenhuma
  port, nenhum adapter Supabase, nem os apps Cliente/Admin.

## Dependencies

- Nenhuma — é a fundação do modo demo do Lojista (10.4 depende desta).
- Padrão de referência (não dependência de código): `clientesCredenciaisFixture`
  (`packages/core-data/src/mock/fixtures/clientes.ts`, login demo do
  Cliente) e o admin semeado `admin@keepit.com.br` (Story 10.1,
  `apps/admin/src/lib/adminAuth.ts`) — mesmo espírito: uma credencial fixa,
  senha ignorada, que já nasce num estado "pronto para demo".
- Precedente de migração `[] → seedado`: `saquesFixture` (ver comentário em
  `mock/db.ts` linha ~134-136) — já resolveu o mesmo tipo de risco de
  "testes assumem array vazio" que esta story pode encontrar.

## Complexidade

SIMPLE — 1 fixture nova + 2 arrays que passam de `[]` para
`structuredClone(fixture)` + barrel export. Sem lógica de negócio nova, sem
mudança de contrato/port. O único trabalho não-trivial é rodar a suíte de
`@keepit/core-data` e ajustar qualquer assert que dependia dos arrays
nascerem vazios.

## Acceptance Criteria

1. Em build mock (`EXPO_PUBLIC_DATA_SOURCE` não definido como `supabase`),
   abrir o app Lojista → tela de Login → digitar `lojista@keepit.com.br` +
   qualquer senha → **entra direto nas 4 abas** da área logada (Pedidos,
   Catálogo, Financeiro, Perfil), sem passar por Onboarding/Cadastro/
   "Em análise".
2. As 4 abas abrem **cheias**: esteira de pedidos com os 21 pedidos de
   `estab-farmacia-vida`, catálogo com os produtos com foto, Financeiro com
   saldo/extrato não-vazios, Perfil/Configurações com horários — ou seja, o
   dataset já rico de `estab-farmacia-vida` (`db.estabelecimentos`) fica
   acessível assim que o gate de login é destravado.
3. `db.lojistaContas` e `db.estabelecimentosCadastrados`, logo após
   `createMockDb()`, contêm **exatamente 1 entrada demo cada** (a fixture
   nova) — nenhum dos dois nasce mais `[]`.
4. `sessionLojistaUserId` continua iniciando `null` em `createMockDb()` — o
   seed **não** loga automaticamente; a sessão só é criada pelo `signIn` real
   (mesmo padrão de `sessionClienteId`).
5. A entrada demo satisfaz as invariantes exigidas por
   `estabelecimento-cadastro.mock.ts#getMeuEstabelecimento`:
   `conta.id === cadastro.donoUserId` (senão o gate devolve `null`/retomada
   de wizard, nunca `'ativo'`); `cadastro.status === 'ativo'`;
   `cadastro.motivoRejeicao === null`; `cadastro.id === 'estab-farmacia-vida'`
   (mesmo `id` do domínio de Descoberta rico, `db.estabelecimentos`); `cnpj`
   idêntico entre `conta` e `cadastro`.
6. O CNPJ semeado é **válido** pelo algoritmo de `apps/lojista/src/lib/cnpj.ts`
   (`isCnpjValido`) — coerência caso alguém abra Perfil/Configurações na
   demo (não é exercido pelo login, mas evita dado inconsistente).
7. O fluxo de `signUp` continua funcionando para um e-mail **diferente** do
   semeado: cria uma conta nova em `db.lojistaContas` e um cadastro
   `'em_analise'` em `db.estabelecimentosCadastrados`, preservando as telas
   `EmAnalise`/`CadastroRejeitado`/retomada de wizard (o wizard não é
   afetado pelo seed, que é uma linha à parte).
8. **Nenhum** caminho de código semeia `lojistaContas`/
   `estabelecimentosCadastrados` fora de `createMockDb()` — em
   `source: 'supabase'` os adapters `lojista-auth.supabase.ts`/
   `estabelecimento-cadastro.supabase.ts` são usados, e `createMockDb()`
   nunca é instanciado (verificável por leitura de `dataClientBootstrap.ts`/
   `src/index.ts` — nenhuma mudança nova é necessária aqui, é uma
   confirmação, não uma tarefa).
9. `pnpm --filter @keepit/core-data test` passa 100% verde. Se algum teste
   dependia dos dois arrays nascerem `[]` (asserts de contagem absoluta em
   vez de relativa a "antes"/"depois"), o assert é corrigido e a mudança é
   documentada no Dev Agent Record — precedente já resolvido com
   `saquesFixture`.
10. A credencial de demo (`lojista@keepit.com.br`, senha qualquer) fica
    documentada no JSDoc da fixture nova (mínimo obrigatório desta AC); um
    README de demo, se existir no repo, pode ser atualizado como extra, mas
    não é obrigatório criar um novo documento só para isso.

### Diagnóstico (por que o gate está trancado hoje)

- `Login.tsx` (`apps/lojista/src/screens/auth/Login.tsx`) chama
  `client.lojistaAuth.signIn(email, senha)` e, com sucesso, lê
  `client.estabelecimentoCadastro.getMeuEstabelecimento()`. Só o ramo
  `status === 'ativo'` chama `signInLojista()`

  `auth.mock.ts`/`adminAuth.ts`) e grava `db.sessionLojistaUserId`.
  `estabelecimento-cadastro.mock.ts#getMeuEstabelecimento` procura em
  `db.estabelecimentosCadastrados` pelo `donoUserId === sessionLojistaUserId`
  e devolve `{ status, motivo_rejeicao }`.
- `db.ts` inicializa **ambos vazios** hoje (`lojistaContas: []`,
  `estabelecimentosCadastrados: []`, linhas ~147/149). Resultado: e-mail
  desconhecido → `signIn` lança `Error` → banner de erro no Login; um
  cadastro feito pelo wizard nasce `'em_analise'` → tela `EmAnalise`, nunca
  `'ativo'`. A porta fica trancada — **não há nenhum caminho hoje para ver
  as 4 abas em modo mock**.
- As telas de `MainTabs` **já leem** um id de estabelecimento fixo,
  `CURRENT_ESTABELECIMENTO_ID = 'estab-farmacia-vida'`
  (`apps/lojista/src/screens/catalogo/currentStore.ts`), de
  `db.estabelecimentos` (domínio de Descoberta, `StorePort`) — que já é
  `'ativo'` e rico (21 pedidos, 15+ produtos, horário amplo). **Essa parte
  já funciona e não precisa de nenhuma mudança.** O que falta é
  exclusivamente destravar o gate de login, que lê um array PARALELO

### Risco principal — testes que assumem os arrays vazios

O JSDoc atual de `db.ts` diz literalmente "o piloto sempre começa vazio" —
mas o spot-check feito no design não encontrou nenhum `toHaveLength(0)`/
`toEqual([])` hard-coded contra `lojistaContas`/`estabelecimentosCadastrados`
em `lojista-auth.mock.test.ts` ou `estabelecimento-cadastro.mock.test.ts`
(os asserts existentes usam `const antes = db.X.length` e comparam
`antes + 1`/`antes`, o que é robusto a um array que já nasce com 1 item).
Ainda assim, **rodar a suíte inteira** é obrigatório (Task 4) — pode haver
um teste fora desses dois arquivos, ou um caso não coberto pelo spot-check,
que dependa da contagem absoluta. Precedente já resolvido: `saquesFixture`
migrou de `[]` para semeado e precisou de ajustes pontuais de assert — se
algo similar acontecer aqui, é esperado e documentável, não um bloqueio.
