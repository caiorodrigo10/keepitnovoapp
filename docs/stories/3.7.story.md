## Status

Done

## MVP Pilot Classification

- Classificação: CORE
- Fonte: `docs/prd/07-plano-mvp-piloto.md` (Épico 3, linha "3.4–3.7 | CORE |
  Cadastro operacional, estado em análise e aprovação pelo Admin.")
- Backend esperado: leitura real de `estabelecimentos` com
  `status = 'em_analise'` via Supabase (`AdminPort.pendingStores`/

## Story

**As a** admin Keepit,
**I want** ver todos os lojistas em status `em_analise` com seus dados,
**so that** eu possa aprovar ou rejeitar cada um.

## Acceptance Criteria

1. A rota já existente `/aprovacoes` (Admin web, entregue mock na Story
   0.12) lista, com dados reais quando `DATA_SOURCE=supabase`, os
   estabelecimentos com `status = 'em_analise'`. **Nota de fidelidade de
   interface:** o texto original do épico usa o caminho
   `/admin/lojistas/pendentes` — esta Story preserva a rota já entregue
   (`/aprovacoes`) em vez de renomear/duplicar, seguindo a política de
   preservação do piloto ("componentes, assets e rotas existentes não são
   apagados", `docs/prd/07-plano-mvp-piloto.md`). [Fonte:
   `docs/prd/epics/3-lojista-aprovacao.md` Story 3.7 AC1]

2. A lista exibe, por lojista pendente: nome fantasia, CNPJ, categoria,
   telefone, data de cadastro (`criado_em`), e ações (aprovar/rejeitar —
   linkam para Stories 3.8/3.9, já roteadas hoje para `/aprovacoes/[id]`).
   Requer estender o contrato exposto ao Admin com `cnpj`, `telefone` e
   `criado_em` (ausentes de `StorePort.Estabelecimento` hoje — ver
   Dependencies). [Fonte: `docs/prd/epics/3-lojista-aprovacao.md` Story
   3.7 AC2]

3. Clicar em um lojista pendente abre o detalhe (`/aprovacoes/[id]`, já
   existente) com todos os dados dos 3 passos do cadastro (nome fantasia,
   CNPJ, responsável, telefone, categoria, endereço, raio, tempo médio,
   taxa de deslocamento, ticket mínimo, chave PIX + tipo, horários), a
   foto de fachada (URL assinada de curta expiração, bucket privado
   `fachadas` — mesmo padrão de `docs/architecture/05-security.md §6.7`) e
   `dados_receita`. No piloto, `dados_receita` é sempre `NULL` (Story 3.3
   é `SIMPLE` — BrasilAPI opcional, não preenche o campo) — a tela exibe
   honestamente "não coletado" nesse caso, nunca um dado inventado ou
   placeholder que pareça real. [Fonte:
   `docs/prd/epics/3-lojista-aprovacao.md` Story 3.7 AC3;
   `docs/architecture/03-data-models.md#1.4`]

4. RLS permite acesso de leitura a `estabelecimentos` (além do próprio
   dono) apenas a admins, via `is_admin()` — policy `admin_gerencia_estab`
   (`docs/architecture/05-security.md §3.4`). Um usuário autenticado sem
   entrada em `admin_users` não vê estabelecimentos de terceiros. [Fonte:
   `docs/prd/epics/3-lojista-aprovacao.md` Story 3.7 AC4;
   `docs/architecture/05-security.md §3.4`]

5. Migration cria `admin_users (id uuid PK REFERENCES auth.users(id),
   nome text NOT NULL, criado_em timestamptz)` e a função
   `is_admin(user_id uuid DEFAULT auth.uid()) RETURNS boolean` (
   `SECURITY DEFINER`, `STABLE`), com RLS própria da tabela
   (`admin_le_admins`, `sem_insert_direto_admins`). [Fonte:
   `docs/prd/epics/3-lojista-aprovacao.md` Story 3.7 AC5;
   `docs/architecture/03-data-models.md#1.7`;
   `docs/architecture/05-security.md §3.7`]

6. O login do Admin web é **e-mail + senha** via Supabase Auth (decisão
   10.4) — **sem SMS, sem 2FA e sem SSO no piloto**. Quando
   `DATA_SOURCE=supabase`, `/login` (já existente, hoje só o mock
   `adminAuth.ts`) autentica de fato contra o Supabase Auth do projeto;
   falha de credencial exibe erro real, sem simular sucesso — em falha,
   nenhuma sessão/token de admin é persistida e `RequireAdminSession`
   continua bloqueando o acesso a `/aprovacoes`. [Fonte:
   `docs/prd/epics/3-lojista-aprovacao.md` Story 3.7 AC6;
   `docs/architecture/05-security.md §5`]

7. `admin_users` é uma **lista plana sem coluna de papel** (todo admin
   pode tudo) e contas são **provisionadas manualmente via SQL** — sem
   tela de auto-cadastro nem de convite de admin nesta Story. Esta AC
   reflete a **decisão 10.6, já RATIFICADA** (`docs/PERGUNTAS_REGRAS_NEGOCIO.md`,
   Rodada 8, 2026-08-02) — não é mais uma decisão técnica provisória; não
   é reaberta por esta Story. [Fonte:
   `docs/prd/epics/3-lojista-aprovacao.md` Story 3.7 AC7;
   `docs/architecture/03-data-models.md#1.7`]

## Dev Notes

### Contexto e limites

- As rotas `/login`, `/aprovacoes` e `/aprovacoes/[id]` já existem
  fielmente desde as Stories 0.12/0.13/10.1 — esta Story **não precisa
  redesenhar nenhuma tela**; o trabalho central é religar dados/sessão
  mock para reais. [Source: `apps/admin/app/(dashboard)/aprovacoes/page.tsx`,
  `apps/admin/app/(dashboard)/aprovacoes/[id]/page.tsx`,
  `apps/admin/app/(auth)/login/page.tsx`]
- `useAdminPendingStores` (hook local do Admin) já consome
  `client.admin.pendingStores()` via `getDataClient()` — nenhuma mudança
  de hook esperada, só o adapter por trás muda quando `DATA_SOURCE=supabase`.
  [Source: `apps/admin/src/hooks/useAdminPendingStores.ts`]
- `AdminSessionProvider`/`RequireAdminSession` hoje dependem
  inteiramente de `apps/admin/src/lib/adminAuth.ts`, que é **local ao app
  Admin** (não usa `@keepit/core-data`/nenhuma port existente) — persiste
  a sessão em `sessionStorage` e um array `ADMINS` hardcoded com 1 entrada
  (`admin@keepit.com.br`). É este módulo que precisa ganhar um caminho
  real (Supabase Auth) — decisão de @architect se isso vira uma port
  dedicada em `packages/core-data` (mesmo padrão de `AuthPort`/
  `LojistaAuthPort`) ou permanece local ao Admin usando
  `@keepit/supabase-client` diretamente. [Source:
  `apps/admin/src/lib/adminAuth.ts`,
  `apps/admin/src/providers/AdminSessionProvider.tsx`,
  `apps/admin/src/components/RequireAdminSession.tsx`]
- `AdminPort.pendingStores`/`approve`/`reject` já têm mock funcional
  completo (`admin.mock.ts`) desde o Épico 0 — o adapter Supabase
  (`admin.supabase.ts`) é hoje um esqueleto que lança
  `NotImplementedError(PORT, 'pendingStores', 'Épico 3')` para os 3
  métodos. Esta Story implementa `pendingStores`/leitura de detalhe;
  `approve`/`reject` ficam para as Stories 3.8/3.9. [Source:
  `packages/core-data/src/mock/admin.mock.ts`,
  `packages/core-data/src/supabase/admin.supabase.ts`]
