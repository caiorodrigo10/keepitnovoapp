## Story

**As a** sistema,
**I want** um ledger financeiro append-only e uma view SQL que agregue o
saldo do lojista a partir dele,
**so that** toda consulta de carteira (disponível, bloqueado, sacado,
debitado) seja consistente e auditável — nunca uma soma recalculada só na
UI.

## Acceptance Criteria

1. Migration cria a tabela `lancamentos_financeiros` conforme
   `docs/architecture/03-data-models.md` §6.1 (DDL já especificado):
   colunas `id`, `estabelecimento_id` (FK `estabelecimentos`, `RESTRICT`),
   `pedido_id` (FK `pedidos`, nullable, `RESTRICT`), `tipo` (`CHECK IN
   ('charge','platform_fee','merchant_credit','refund','payout')`),
   `valor_centavos bigint` (assinado, imutável), `status` (`CHECK IN
   ('pendente','concluido','erro')`, default `'concluido'`),
   `asaas_id_externo`, `ator_admin_id` (FK `auth.users`), `detalhe`,
   `disponivel_em timestamptz` (nullable), `criado_em`, `concluido_em`.
   Índices: `idx_lancamentos_estab (estabelecimento_id, disponivel_em)`,
   `idx_lancamentos_pendentes (status, criado_em) WHERE status =
   'pendente'`, `idx_lancamentos_pedido (pedido_id) WHERE pedido_id IS NOT
   NULL`. [Fonte: `03-data-models.md` §6.1]
2. Trigger `trg_lancamento_imutavel` (função
   `lancamento_financeiro_imutavel()`) bloqueia `UPDATE` de
   `valor_centavos`, `tipo`, `estabelecimento_id`, `pedido_id`,
   `criado_em` — só `status`, `asaas_id_externo`, `ator_admin_id`,
   `detalhe`, `concluido_em` podem sofrer `UPDATE` (passo manual do
   Admin). Correção de um lançamento errado exige um NOVO lançamento
   (estorno + relançamento), nunca `UPDATE` do valor. [Fonte:
   `03-data-models.md` §6.1, bloco "Imutabilidade do valor"]
3. Migration cria a view `carteira_lojista` conforme `03-data-models.md`
   §6.2 (SQL já especificado): `SUM`/`FILTER` sobre
   `lancamentos_financeiros` produzindo `estabelecimento_id`,
   `saldo_disponivel_reais`, `saldo_bloqueado_reais`, `total_sacado_reais`,
   `total_debitado_reais` — os MESMOS 5 campos que
   `packages/core-data/src/ports/wallet.port.ts#CarteiraLojista` já define
   (nenhuma mudança de contrato). `ALTER VIEW carteira_lojista SET
   (security_invoker = true)` (mesmo padrão de `05-security.md` §3.13,
   agora sobre a tabela única). A regra D+7 usa
   `businessConfig.carteiraLiberacaoDias` (7) — o número não fica solto na
   migration; é o mesmo valor gravado em `disponivel_em` no momento em que
   `confirmar_pin_pedido` marca `entregue_em` (Story 7.12 grava esse
   campo; esta Story só consome `disponivel_em <= NOW()` na `FILTER`).
4. RLS: `lancamentos_financeiros` com `ENABLE`+`FORCE ROW LEVEL SECURITY`.
   Policy de leitura: lojista vê os próprios lançamentos
   (`estabelecimento_id = meu_estabelecimento_id()`), admin vê tudo
   (`is_admin()`) — mesmo padrão de `05-security.md` §3.12
   (`lojista_ve_proprios_saques`/`lojista_ve_proprios_debitos`), adaptado
   à tabela única. Nenhuma policy de `INSERT`/`UPDATE`/`DELETE` para
   `authenticated`/`anon` (`WITH CHECK (false)` explícito ou ausência de
   policy permissiva) — toda escrita passa exclusivamente por RPC
   `SECURITY DEFINER` (Stories 7.8/7.12, futuramente Bloco 09).
5. Testes SQL/RPC (via MCP `execute_sql`, documentados no PR/registro da
   migration) verificam, **conforme o Model B efetivamente aplicado** (o
   `merchant_credit` carrega o valor LÍQUIDO; `charge`/`platform_fee` são
   lançamentos de auditoria que **não** entram na carteira): (a) um
   `merchant_credit` (líquido) com `disponivel_em` no futuro aparece em
   `saldo_bloqueado_reais`, não em `saldo_disponivel_reais` — e um
   `charge`/`platform_fee` do mesmo pedido **não** altera nenhum dos dois
   saldos (auditoria pura); (b) o mesmo `merchant_credit` com
   `disponivel_em` no passado aparece em `saldo_disponivel_reais`; (c) um
   `payout` negativo com `status <> 'erro'` reduz `saldo_disponivel_reais`
   e aumenta `total_sacado_reais`; (d) uma tentativa de `UPDATE
   valor_centavos` ou `tipo` em uma linha existente lança exceção
   (trigger); (e) lojista A não enxerga lançamentos do lojista B via RLS;
   (f) admin enxerga lançamentos de todos os lojistas.

| `platform_fee` | − | Não (auditoria — comissão de 10%, já deduzida do líquido) |
| `merchant_credit` (crédito de pedido) | + (líquido) | Sim, sujeito a D+7 |
