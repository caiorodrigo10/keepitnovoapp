## Status

## MVP Pilot Classification

- Classificação: SIMPLE (roteiro manual, sem automação)

conhecidos.

## Acceptance Criteria

1. Documento `docs/tests/smoke-pilot-ios-mock.md` (diretório `docs/tests/`
   ainda não existe — esta story o cria) com passo a passo dos dois apps
   rodando em mock:
   - **Cliente:** onboarding (`Onboarding1`/`Onboarding2`/`Onboarding3`) →
     login mock (`Login.tsx`/`CriarConta.tsx`) → hub (`Hub.tsx`) → loja
     (`Loja.tsx`) → produto (`DetalheProduto.tsx`) → checkout
     (`Carrinho.tsx`/`Checkout.tsx`/`Pagamento.tsx`) → PIN
     (`ModalConfirmarPin.tsx`) → recibo (`Recibo.tsx`).
   - **Lojista:** login mock (`Login.tsx`, Story 9.0.4) → dashboard
     (`financeiro/Dashboard.tsx`) → pedido (`pedidos/NovosPedidos.tsx` →
     `AceitarPedido.tsx`) → PIN (`pedidos/DigitarPin.tsx`) → carteira
     (`financeiro/Carteira.tsx`).
   [Fonte: `docs/prd/epics/9-publicacao-compliance.md`, Story 9.0.8 AC1 —
   nomes de tela ajustados aos arquivos reais do repositório, confirmados
   por leitura nesta análise]
2. Cada passo tem critério de "OK" visual (ex.: "tela X abre com o título Y
   visível", "recibo mostra valor e hub corretos"). [Fonte: idem, AC2]
3. O roteiro declara explicitamente que é **mock**: sem cobrança PIX real,
   sem push real, cartão inativo. [Fonte: idem, AC3]
4. O roteiro registra a **necessidade de dois aparelhos** (um com o app
   Cliente, um com o app Lojista) para exercitar um pedido ponta-a-ponta, já
   que os controles de dev foram ocultados (Story 9.0.5) — sem
   `OrderStatusDevAdvancer`, não há como avançar o status do pedido num
   único device. [Fonte: idem, AC4; Story 9.0.5, seção Riscos]
5. Distinto da Story 9.4 (smoke da Fase Real, que cobre backend/produção);
   este é o smoke enxuto do piloto mock. O documento deve deixar essa
   distinção explícita no cabeçalho, para não ser confundido com o roteiro
   da 9.4 quando ela existir. [Fonte: idem, AC5]

- **Lojista** (`apps/lojista/src/screens/`): `auth/Login.tsx` (Story 9.0.4),
  `financeiro/Dashboard.tsx`, `pedidos/NovosPedidos.tsx`,
  `pedidos/AceitarPedido.tsx`, `pedidos/DigitarPin.tsx`,
  `financeiro/Carteira.tsx`.

### Relação com a Story 9.0.5 (por que o aviso de dois aparelhos é obrigatório)

A Story 9.0.5 confirma que `OrderStatusDevAdvancer` já é `__DEV__`-only e,
portanto, não aparece no build de release do piloto. Sem esse controle, o
único jeito de mover um pedido de "aguardando aceite" até "concluído" é o
app Lojista de verdade aceitando/confirmando o PIN — o que exige um segundo
aparelho (ou o mesmo aparelho trocando de app, se o stakeholder só tiver um
iPhone — registrar essa alternativa no roteiro como aceitável, mesmo que
menos prática).
