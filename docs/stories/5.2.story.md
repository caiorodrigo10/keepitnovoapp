## Data Mode

- Entidades: `estabelecimentos`, `estabelecimentos_hubs`.
- Modo padrão: mock (`DATA_SOURCE=mock`) — `store.mock.ts#listByHub`
  **ignora `hubId`** e retorna todas as lojas `ativo` (simplificação
  documentada desde a Story 0.2/1.10, porque o mock não modela a junção
  loja↔hub — só há 1 hub "completo" nas fixtures). Este comportamento
  **não é alterado por esta Story** — é uma divergência mock↔real já
  aceita (ver Dev Notes), preservando a navegabilidade de demonstração.
- Modo real: `DATA_SOURCE=supabase` habilita `StorePort.listByHub` real
  contra a junção `estabelecimentos_hubs` × `estabelecimentos` — hoje
  stub `NotImplementedError('Épico 5')` em `store.supabase.ts`.
- Compatibilidade mock: `DATA_SOURCE=mock` preserva a tela do Hub
  (`Hub.tsx`, Story 0.5) mostrando as lojas mock existentes, sem
  alteração.
- Modo híbrido: proibido nesta Story.

## Dependencies

- **Migration `20260812213002_criar_estabelecimentos_hubs.sql` já
  aplicada** (`@data-engineer`, 2026-08-12): tabela de junção pura
  (`estabelecimento_id`, `hub_id`, PK composta, FKs `ON DELETE CASCADE`),
  índice `idx_estab_hubs_hub`, RLS `publico_ve_estab_hubs` (fail-closed:
  só expõe o par se `hubs.ativo = true` **E**
  `estabelecimentos.status = 'ativo' AND pausado_manualmente = false AND
  excluido_em IS NULL`) + `admin_gerencia_estab_hubs` (só admin
  escreve). **Nenhuma migration/RLS nova é necessária para esta Story.**
- `estabelecimentos` e `hubs` já existem, reais, com RLS aplicada
  (blocos 02/03/04) — Stories 3.4/3.5 e 4.1.
- 🔴 **BR-HUB não decidida (pendência do Caio, `docs/orchestration/PENDENCIAS-CAIO.md`)**
  — "Como a loja é vinculada ao hub? (auto na aprovação / Admin seleciona /
  lojista escolhe)". Hoje **só o admin** escreve em
  `estabelecimentos_hubs` (`admin_gerencia_estab_hubs`); não existe UI
  nem RPC de população. Enquanto a associação não for populada,
  `listByHub` retorna **0 linhas para qualquer hub** — comportamento
  honesto e verificável (estado vazio da UI), **não simulado**. Esta
  Story **não decide nem implementa** o mecanismo de população — apenas
  a leitura, que já funciona assim que a associação existir.
- UI (`Hub.tsx` via `useStoresList`/`StorePort.listByHub`, Story 0.5) já
  trata o estado vazio ("Nenhuma loja neste hub ainda.") — nenhuma
  mudança de UI necessária.
- Story 5.3 (estado da loja) e 5.4 (catálogo) consomem o mesmo tipo
  `Estabelecimento` retornado aqui, mas via `StorePort.getById`
  (já real, Stories 4.7/4.8) — esta Story não precisa esperar por elas.

## Complexidade

MEDIUM — a query em si (join de duas tabelas já reais, RLS já aplicada) é
simples; a complexidade está em documentar honestamente o recorte
leitura-pronta/população-pendente sem simular dados e em cobrir os casos
de teste (hub sem associação, loja pausada/excluída mesmo que associada).

## Scope

**Incluído:** adapter Supabase real de `StorePort.listByHub` — `SELECT`
em `estabelecimentos` via `estabelecimentos_hubs.hub_id = :hubId`, com
filtro explícito de `status = 'ativo' AND pausado_manualmente = false AND
excluido_em IS NULL` no client (defesa em profundidade, mesmo padrão de
`product.supabase.ts#list`, mesmo que a RLS já garanta isso); testes
unitários (hub com lojas associadas retorna as lojas; hub sem associação
retorna `[]`; loja pausada/inativa associada não aparece).

**Excluído:** popular `estabelecimentos_hubs` (BR-HUB, pendência do
Caio — nenhuma UI/RPC de vínculo é criada aqui); Haversine/
`raio_atendimento_km`/matching geográfico; Edge Function dedicada
(`lojas-por-hub`, substituída pela query direta filtrada por RLS);
qualquer mudança de UI (`Hub.tsx` já trata o estado vazio).
