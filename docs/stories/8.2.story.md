## Ajuste de piloto (obrigatório — ler antes de implementar)

Esta Story **NÃO** chama nenhuma API externa (Asaas). O botão "Executar
reembolso" é **um passo manual auditável**: o admin confirma que já fez (ou
vai fazer) o PIX/estorno de fato **fora do sistema**, e o sistema apenas
registra essa confirmação — `status: 'pendente' → 'concluido'` (sucesso) ou
`'pendente' → 'erro'` (falha, com detalhe) no lançamento
`lancamentos_financeiros` correspondente, com `ator_admin_id`,
`concluido_em` e opcionalmente `asaas_id_externo` (se o admin quiser
registrar a referência do PIX manual feito fora do fluxo). **Nenhum sucesso
de estorno externo é simulado** — o sistema não afirma "estornado" no
sentido de "o Asaas de fato processou"; afirma "o admin confirmou a
execução manual, com auditoria". Esta é uma seam honesta: quando o Bloco
08-PIX ligar a Edge Function real, o mesmo botão passa a refletir o
resultado real da chamada Asaas, sem mudar a UI.

Segue a mesma decisão já aplicada para o repasse ao lojista (`solicitar_saque`,
Bloco 08 — "não move dinheiro, só registra a intenção/confirmação; o admin
executa o PIX real fora do fluxo automatizado", `docs/architecture/07-mvp-pilot-backend.md`
§"Financeiro mínimo").

## Story

**As a** admin,
**I want** clicar "Executar reembolso" e o sistema registrar a execução de
forma auditável,
**so that** eu não precise editar o banco na mão e o histórico financeiro
fique íntegro.

## Acceptance Criteria

1. Botão "Executar" no item da fila (já existente, `/reembolsos`).
   Confirmação com modal ("Você vai estornar R$ {X} ao cliente. Confirma?")
   — já implementada em mock, preservada sem mudança de texto/layout.
   [Fonte: `docs/prd/epics/8-admin-operacao.md` Story 8.2 AC1]

2. **AJUSTADO PARA O PILOTO (ver seção "Ajuste de piloto" acima).** Ao
   confirmar, uma RPC `SECURITY DEFINER` (a) marca o lançamento como
   `status = 'concluido'` (sucesso, equivalente a "estornado" na UI) ou
   `status = 'erro'` com `detalhe` preenchido (falha), (b) grava
   `ator_admin_id = auth.uid()` e `concluido_em = NOW()`. **Não há chamada
   Asaas nem estado intermediário persistido `em_processamento`** — o texto
   original do Épico ("Edge Function `executar-reembolso` chama Asaas
   `estornarCobranca`") descreve o modelo-alvo pós-Bloco-08-PIX, fora do
   escopo desta Story. Nenhum sucesso de estorno externo é simulado — a UI
   reflete apenas a confirmação manual auditada. [Fonte:
   `docs/prd/epics/8-admin-operacao.md` Story 8.2 AC2, ajustado pelo plano
   do Bloco 09 e por `docs/architecture/07-mvp-pilot-backend.md` §"Financeiro
   mínimo"]

3. Se reembolso parcial (ex.: 90%), o valor ao lojista fica registrado como
   um lançamento `merchant_credit` positivo pareado — **fora do escopo
   desta Story** (nenhum produtor de reembolso parcial existe ainda no
   Bloco 09; ver Story 8.1 Dependencies item 3). Quando o Bloco 10
   implementar os produtores parciais, esta AC passa a valer sem mudança no
   RPC de confirmação (que só marca `status`, não recalcula valores). [Fonte:
   `docs/prd/epics/8-admin-operacao.md` Story 8.2 AC3]

4. Push ao cliente quando concluído — **LATER (polling)**, explicitamente
   fora do piloto conforme `docs/orchestration/BLOCO-09-ADMIN-OPS-2026-08-13.md`
   "Fronteira / FORA". Não implementado nesta Story. [Fonte:
   `docs/prd/epics/8-admin-operacao.md` Story 8.2 AC4, ajustado pelo plano
   do Bloco 09]

5. Logs de auditoria (`admin_id`, `pedido_id`, valor, timestamp) — **já
   nativos do ledger**: `ator_admin_id`, `pedido_id` (via FK do próprio
   lançamento), `valor_centavos` (imutável desde a criação),
   `concluido_em`. Nenhuma tabela de auditoria separada é necessária —
   `lancamentos_financeiros` já é o registro auditável append-only. [Fonte:
   `docs/prd/epics/8-admin-operacao.md` Story 8.2 AC5;
   `docs/architecture/03-data-models.md §6.1`]

## Dev Notes

### Contexto e limites

- A UI (`/reembolsos`, botão "Executar" + modal) já existe fielmente desde
  a Story 0.13 — esta Story só precisa religar o `process` do mock para o
  adapter Supabase real. [Source:
  `apps/admin/app/(dashboard)/reembolsos/page.tsx`]
- **Nada de Edge Function nesta Story.** O critério do overlay
  (`docs/architecture/07-mvp-pilot-backend.md` §"Edge Functions mínimas") é
  claro: "Edge Function só quando há segredo server-side ou validação de
  origem externa (Asaas)". Confirmar execução manual não toca segredo nem
  origem externa — é autorização + escrita no banco, resolvida com RLS +
  RPC `SECURITY DEFINER`, mesmo padrão de `confirmar_pin_pedido` e
  `solicitar_saque`. [Source: `docs/architecture/07-mvp-pilot-backend.md`]
- **Precedente estrutural:** `solicitar_saque`
  (`apps/supabase/supabase/migrations/20260813050004_rpc_solicitar_saque.sql`)
  já mostra o padrão de RPC `SECURITY DEFINER` + `search_path=''` +
  validação server-side + retorno tipado sobre `lancamentos_financeiros` —
  usar como referência de estilo/hardening para o novo RPC desta Story
  (guard diferente: `is_admin()` em vez de dono do estabelecimento).
  [Source: `apps/supabase/supabase/migrations/20260813050004_rpc_solicitar_saque.sql`]
