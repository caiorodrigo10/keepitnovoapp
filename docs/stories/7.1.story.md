## Story

**As a** dev,
**I want** um wrapper HTTP tipado do Asaas reutilizável pelas Edge

## Acceptance Criteria

1. `apps/supabase/supabase/functions/_shared/asaas.ts` exporta uma factory
   `createAsaasClient(overrides?)` que retorna um objeto com os métodos:
   `criarCliente`, `criarCobranca`, `obterQrCodePix`, `estornarCobranca`,
   `criarTransferencia`, `criarSubconta`, `tokenizarCartao`. Os 5 primeiros
   (`criarCliente`, `criarCobranca` com `billingType: 'PIX'`,
   `obterQrCodePix`, `estornarCobranca`, `criarTransferencia`) fazem a
   chamada HTTP real ao Asaas. `criarSubconta` e `tokenizarCartao` (e
   `billingType: 'CREDIT_CARD'` em `criarCobranca`) são stubs reservados:
   tipados, chamáveis, retornam `{ ok: false, error: { code:
   'NOT_IMPLEMENTED_PILOT', message: '...', status: 0 } }` **sem fazer
   nenhuma chamada HTTP** — testável por asserção de que o `fetch`
   injetado não foi chamado.
2. O client lê `ASAAS_API_KEY` e `ASAAS_ENVIRONMENT` via
   `Deno.env.get(...)` — a leitura acontece **dentro** do corpo de
   `createAsaasClient()` (ou de um helper chamado por ele), nunca no nível
   de módulo (`import`/top-level). Se `ASAAS_BASE_URL` estiver setada no
   env, ela tem prioridade absoluta sobre a derivação por
   `ASAAS_ENVIRONMENT`; senão, a base URL é derivada:
   `ASAAS_ENVIRONMENT === 'production'` → `https://api.asaas.com/v3`,
   qualquer outro valor (inclusive ausente) → sandbox,
   `https://api-sandbox.asaas.com/v3` (default seguro — nunca cai em
   produção por omissão). `createAsaasClient(overrides)` aceita
   `{ apiKey?, baseUrl?, fetchImpl? }` para permitir testes 100% offline
   sem depender de variáveis de ambiente reais.
3. Toda chamada HTTP usa o header `access_token: <apiKey>` (nunca
   `Authorization: Bearer`, que não é o padrão do Asaas) e
   `Content-Type: application/json`. Nenhum método lança exceção: erros de
   rede (fetch rejeita) e respostas HTTP não-2xx são capturados e
   normalizados no mesmo formato `AsaasResult<T>` de sucesso — nunca um
   `throw` escapa de um método público do client. `AsaasResult<T> = { ok:
   true; data: T } | { ok: false; error: AsaasError }`, com `AsaasError =
   { status: number; code?: string; message: string; details?: unknown }`.
   Erro de rede usa `status: 0`.
4. Cada um dos 5 métodos ativos tem pelo menos: 1 teste de caminho feliz
   (fetch mockado retorna a fixture de sucesso, `ok: true` com os campos
   esperados), 1 teste de erro HTTP (fetch mockado retorna 4xx/5xx,
   `ok: false` com `status` correto), e o teste de erro de rede é coberto
   uma vez de forma genérica (não precisa repetir para os 5 métodos). Os 2
   stubs (`criarSubconta`, `tokenizarCartao`) têm teste confirmando que
   retornam `NOT_IMPLEMENTED_PILOT` **sem invocar** o `fetch` injetado
   (usar um mock que falha o teste se for chamado). Fixtures de resposta
   real do Asaas (baseadas em `asaas-api-reference.md`) vivem em
   `apps/supabase/supabase/functions/_shared/__fixtures__/` — no mínimo
   `customer.json`, `payment-pix.json`, `pix-qr-code.json`.
5. `apps/supabase/supabase/functions/_shared/README.md` documenta: (a)
   como rodar os testes offline (`deno test`, comando exato); (b) para
   cada um dos 5 métodos ativos, como testá-lo manualmente contra o
   sandbox real do Asaas uma vez que `ASAAS-1` (conta aprovada) e
   `ASAAS-2` (secrets setados nas Edge Functions do `keepit-dev`)
   estiverem resolvidos — incluindo o passo de registrar o webhook
   (`POST /v3/webhooks`) mencionado em `asaas-api-reference.md`, mesmo que
   o handler do webhook seja de uma Story futura (7.5); (c) nota explícita
   de que `criarSubconta`/`tokenizarCartao` são stubs não testáveis contra
   sandbox nesta fase (piloto de conta única, cartão deferido).
6. `apps/supabase/package.json` troca os scripts `test`, `typecheck` e
   `lint` (hoje `"echo skipped"`) por comandos `deno` reais que cobrem
   `supabase/functions/_shared/` (ex.: `deno test --allow-env`,
   `deno check`, `deno lint`). `pnpm qa` na raiz do monorepo (via turbo)
   continua verde após a mudança — se o binário `deno` não estiver
   disponível no ambiente de execução, isso é um bloqueio de setup a ser
   resolvido (instalar Deno), não um motivo para deixar o script como
   no-op novamente.

### Convenção de erro (Result tipado)

```ts
type AsaasResult<T> =
  | { ok: true; data: T }
  | { ok: false; error: AsaasError };

interface AsaasError {
  status: number;       // 0 = erro de rede (fetch rejeitou antes de responder)
  code?: string;        // "NOT_IMPLEMENTED_PILOT" para os stubs
  message: string;
  details?: unknown;    // corpo bruto da resposta de erro, se parseável
}
```

Nenhum método público lança exceção — é o contrato exigido pelo AC3 (as
Edge Functions consumidoras de 7.2/7.5/7.11 fazem `if (!result.ok) {...}`
sem `try/catch`).

### Por que `deno test`, não Vitest

O runtime de produção deste código é o Edge Runtime do Supabase (Deno 2,
`config.toml` `[edge_runtime] deno_version = 2`) — não o Node.js do resto
do monorepo. `docs/orchestration/PLANO-MERGE-E-ADIANTAR-PAGAMENTOS.md`
Parte B já registra essa decisão ("testes rodam contra fixtures... com
`fetch` injetado/mockado", "Deno test (DB/fetch mockados)"). Isso é uma
mudança de ferramenta de teste em relação ao resto do monorepo (que usa
Vitest via `packages/*`), documentada aqui para não ser confundida com uma
inconsistência — é a ferramenta nativa e correta para código que roda em
Deno. **Atenção de setup**: o binário `deno` pode não estar disponível em
todo ambiente de execução (não estava disponível, por exemplo, no
