## Story

**As a** dev solo,
**I want** navegação real entre todas as telas mock dos 3 apps (Cliente, Lojista, Admin),
**so that** o produto seja percorrível ponta-a-ponta desde cedo, permitindo validar o fluxo completo com o stakeholder antes de qualquer tela receber conteúdo/lógica de negócio real.

## Acceptance Criteria

1. Cliente e Lojista usam **react-navigation** — stack de auth → tab navigator → stacks internas, conforme a estrutura do protótipo.
2. Admin usa Next.js App Router com route groups (`(auth)`, `(dashboard)`) e layout persistente com sidebar.
3. Todos os fluxos ponta-a-ponta são navegáveis (telas ainda podem ser stubs nesta story).
4. Modais (CPF, PIN, permissão push) implementados como rotas modais.
5. Guardas de navegação (auth) são stubs que sempre deixam passar, alternáveis por flag para testar o fluxo deslogado.

### Modal PIN — distinção Cliente x Lojista (importante para não confundir escopo)

- **Cliente**: "Confirmar retirada / PIN" (Story 0.7, AC1) é tratado nesta story como **modal** (`ModalConfirmarPin`), pois representa uma confirmação rápida sobreposta ao fluxo de acompanhamento de pedido, coerente com o AC4 desta story ("Modais (CPF, PIN, permissão push)").
- **Lojista**: "Digitar PIN (tela + teclado)" (Story 0.10, AC1) é uma **tela cheia dentro da PedidosStack**, não um modal — é o teclado numérico que o lojista usa para confirmar a retirada do cliente, uma interação mais longa que não se encaixa no padrão de modal rápido.
- [AUTO-DECISION] Interpretar "PIN" no AC4 do Épico 0 como referindo-se especificamente ao fluxo do Cliente → decisão: manter Lojista como tela cheia (reason: o próprio inventário de telas do Épico 0 já descreve "Digitar PIN (tela + teclado)" como item de lista de telas, não como modal, na Story 0.10; um teclado numérico full-screen é padrão de UX mais comum que um modal para essa interação).
