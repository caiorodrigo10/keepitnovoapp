## Dependencies

- `ModalCPF.tsx` (`apps/cliente/src/screens/modals/ModalCPF.tsx`) já existe
  (Story 0.6, religado à port real na Story 1.10) e já chama
  `client.auth.updateCpf(cliente.id, digits)` + `cart.markCpfCollected()`.
  Já é acionado a partir de `Checkout.tsx#handlePagar` quando
  `!cart.cpfCollected`. **Gaps reais desta Story, não reconstrução:**
  1. `apenasDigitosCnpj`/máscara existe, mas **nenhuma validação de dígito
     verificador** — o próprio JSDoc do arquivo admite: "apenas exibição,
     sem validação real de CPF (BrasilAPI/dígito verificador ficam fora do
     Épico 0)". [Source: `apps/cliente/src/screens/modals/ModalCPF.tsx`
     linhas 15-19]
  2. `AuthPort.updateCpf` no adapter Supabase é **stub**:
     `throw new NotImplementedError(PORT, 'updateCpf', EPIC)`. [Source:
     `packages/core-data/src/supabase/auth.supabase.ts` linhas 380-382]
     O adapter MOCK já persiste (`packages/core-data/src/mock/auth.mock.ts`
     linhas 234-247), mas SEM checar se `cliente.cpf` já existia — sempre
     sobrescreve, o que viola "não pedir de novo"/"nunca sobrescreve um CPF
     já salvo" se algum caminho futuro chamar de novo por engano.
  3. `cart.cpfCollected` é um flag de SESSÃO do `CartContext` (em memória,
     perdido ao reabrir o app) — hoje é a ÚNICA coisa que impede o modal de
     reaparecer. Se o cliente já tem `clientes.cpf` preenchido no backend
     mas abre o app de novo (nova sessão do `CartContext`), o flag volta a
     `false` e o modal reapareceria indevidamente. Esta Story corrige isso
     inicializando `cpfCollected` a partir do dado real do cliente
     (`useCurrentCliente().data?.cpf != null`), não só da flag de sessão.
- Precedente EXATO de validador de dígito verificador no monorepo:
  `apps/lojista/src/lib/cnpj.ts` (`isCnpjValido`, Story 3.3) — algoritmo
  padrão Receita Federal (módulo 11, 2 dígitos verificadores), incluindo a
  rejeição de sequências repetidas (`/^(\d)\1{13}$/`). Mesma decisão de
  localização já tomada para CNPJ ("não promovido para `packages/config`
  — é algoritmo determinístico, não placeholder de negócio") se aplica ao
  CPF: criar `apps/cliente/src/lib/cpf.ts`, local ao app Cliente (único
  consumidor hoje).
- RLS `cliente_atualiza_proprio` (`docs/architecture/05-security.md §3.1`)
  já permite `UPDATE` do próprio cliente — mas o comentário SQL ("não pode
  mudar bloqueado, cpf via UPDATE direto") não é enforced literalmente pelo
  `WITH CHECK` (que só trava `bloqueado`). A trava "só quando `cpf IS NULL`"
  é responsabilidade do ADAPTER (`auth.supabase.ts#updateCpf`), não da RLS
  — implementar como `UPDATE clientes SET cpf = $1 WHERE id = auth.uid()
  AND cpf IS NULL` (0 linhas afetadas porque já tinha CPF → tratar como
  no-op honesto, não erro, já que a UI nunca deveria chamar de novo; 0
  linhas porque a RLS bloqueou outro usuário → erro).
- `Checkout.tsx#handlePagar` já decide `!cart.cpfCollected` → abre
  `ModalCPF` (Story 0.6) — esta Story ajusta a fonte de verdade de
  `cpfCollected` (ver gap 3 acima), sem redesenhar o fluxo de navegação.

## Story

**As a** cliente que nunca fez pedido,
**I want** informar meu CPF uma única vez no primeiro checkout,
**so that** eu tenha NF disponível se pedir.

## Acceptance Criteria

1. Se `clientes.cpf IS NULL` para o cliente autenticado — verificado pelo
   dado REAL do cliente (`AuthPort.currentUser()`/`useCurrentCliente`), não
   apenas pela flag de sessão `cart.cpfCollected` —, o checkout exibe o
   modal obrigatório de CPF antes de prosseguir para o pagamento,
   reaproveitando `ModalCPF.tsx` e a chamada já existente em
   `Checkout.tsx#handlePagar`. `cart.cpfCollected` passa a ser inicializado
   a partir de `cliente.cpf != null` (corrige o gap 3 das Dependencies —
   hoje reabrir o app reapresentaria o modal indevidamente mesmo com CPF
   já salvo). [Fonte: `docs/prd/epics/6-pedido-pin.md` Story 6.5 AC1]

2. Validação de formato + dígitos verificadores do CPF (algoritmo padrão
   da Receita Federal — módulo 11, 2 dígitos verificadores sobre os 9
   dígitos base), em um novo utilitário `apps/cliente/src/lib/cpf.ts`,
   mesmo padrão de `apps/lojista/src/lib/cnpj.ts` (Story 3.3). Rejeita CPF
   com todos os dígitos repetidos (`"00000000000"`, `"11111111111111"`
   etc.) e qualquer entrada com contagem de dígitos diferente de 11. O
   botão "Confirmar" em `ModalCPF` fica desabilitado até o CPF ser
   VÁLIDO (hoje só valida a contagem de 11 dígitos, sem dígito
   verificador). [Fonte: Story 6.5 AC2]

3. O CPF válido é salvo em `clientes.cpf` via `AuthPort.updateCpf` — com
   implementação REAL no adapter Supabase (hoje `NotImplementedError`),
   restrita a `id = auth.uid()` (nunca confia no `clienteId` recebido para
   autorização — mesmo padrão de `updateProfile`, Story 2.8) e só quando
   `cpf IS NULL` ("set once": nunca sobrescreve um CPF já salvo), sob a RLS
   `cliente_atualiza_proprio` já existente (sem migration/RLS nova). O
   adapter mock recebe a mesma trava "set once", por defesa em
   profundidade. Não é solicitado novamente em checkouts futuros — nem
   nesta sessão, nem após reabrir o app (AC1). [Fonte: Story 6.5 AC3]

## Dev Notes

### Contexto e limites

- Esta Story NÃO é "criar a coleta de CPF do zero" — o fluxo de UI
  (`ModalCPF`, gatilho em `Checkout.tsx`, `cart.markCpfCollected`) já existe
  desde a Story 0.6/1.10. O trabalho real é fechar os DOIS gaps de backend
  honesto: (a) o adapter Supabase de `updateCpf` é stub hoje; (b) não existe
  validação de dígito verificador em lugar nenhum. Não redesenhar a UI do
  modal além do necessário para o botão "Confirmar" refletir a validação
  real.
- Mesma decisão de localização de `apps/lojista/src/lib/cnpj.ts` (Story
  3.3) se aplica ao CPF: fica em `apps/cliente/src/lib/`, não em
  `packages/config` (aquele pacote é para placeholders de negócio, não
  algoritmos determinísticos — ver JSDoc de `businessConfig` em
  `packages/config/src/index.ts`).
- A RLS `cliente_atualiza_proprio` (`docs/architecture/05-security.md
  §3.1`) tem um comentário SQL que sugere travar CPF via `WITH CHECK`, mas
  o `WITH CHECK` real só trava `bloqueado` — não confiar nesse comentário
  como se fosse enforcement; a trava "set once" precisa estar no CÓDIGO do
  adapter, não assumida do lado do banco.

### Segurança

- `updateCpf` deve seguir EXATAMENTE o padrão de autorização já
  estabelecido por `updateProfile` (Story 2.8): a sessão atual
  (`auth.uid()`/`getUser().id`) é a ÚNICA fonte de autorização — nunca o
  `clienteId` recebido como parâmetro da função, mesmo que a UI sempre
  passe o id correto hoje. RLS é a segunda barreira, não a primeira.
- CPF é PII sensível — não logar em texto claro além do necessário
  (mesmo cuidado já documentado na Story 2.8 para e-mail/senha/token).

### Testing

- Testes unitários de `cpf.ts`: CPFs válidos conhecidos (gerar por
  algoritmo, não hard-code de CPF real de pessoa); CPFs com DV errado;
  sequências repetidas (`"11111111111"` etc.); menos/mais de 11 dígitos.
- Testes de `auth.supabase.ts`/`auth.mock.ts` `updateCpf`: cliente sem CPF
  → grava; cliente com CPF já existente → não sobrescreve (retorna o
  cliente atual, sem erro); autorização negativa (tentar gravar CPF de
  outro `clienteId` — a chamada real usa a sessão, não deveria nem ser
  possível direcionar a outro usuário).
- `pnpm qa`.
- `pnpm --filter @keepit/cliente typecheck`.
- Teste manual/device com `DATA_SOURCE=supabase`: cliente novo (sem CPF) →
  primeiro checkout pede CPF → confirma com CPF válido → segundo checkout
  (mesma sessão E após reabrir o app) não pede mais.
