## Story

**As a** operador Keepit (usuário interno do painel Admin),
**I want** telas operacionais e financeiras — fila de reembolsos, gestão de pedidos com cancelamento forçado, gestão de clientes/lojistas (bloqueio/suspensão) e dashboard financeiro geral —
**so that** eu consiga operar o dia a dia da Keepit (resolver reembolsos, agir sobre pedidos problemáticos, moderar clientes e lojistas, acompanhar GMV/receita) inteiramente a partir do painel, mesmo antes de existir backend real.

## Acceptance Criteria

1. Telas: Fila de reembolsos, Executar reembolso, Lista de pedidos (filtros), Detalhe + forçar cancelamento, Lista de clientes + bloquear, Suspender lojista, Dashboard financeiro geral (GMV, receita Keepit por período, ranking de lojas), Vista de qualidade do lojista.
2. Dados via `admin.port` / `order.port` mock.
3. Fidelidade visual verificada contra o **design system dark** (`packages/ui-tokens`, consistente com o app Lojista e com a Story 0.12) — o protótipo `keepit-app/index.html` não possui telas Admin, portanto a fidelidade é ao sistema de design extraído, não pixel-a-pixel a um frame inexistente.

### Data Models (schema real — mock deve espelhar nomes de campo)

Todas as ports/mocks devem usar os **mesmos nomes de campo** das tabelas reais, conforme regra do Épico 0 ("As ports espelham o schema real... para o mock não divergir"). [Source: docs/prd/epics/0-casca-visual.md#Arquitetura da fronteira mock/real]

- **`reembolsos_pendentes`**: `id`, `pedido_id`, `motivo` (enum: `timeout_aceite`, `recusa_lojista`, `cancelamento_cliente_pre_aceite`, `cancelamento_cliente_pos_aceite`, `cancelamento_atraso`, `nao_retirado_cliente`, `nao_entregue_lojista`, `chargeback`, `cancelamento_admin`), `valor_a_estornar_reais`, `valor_ao_lojista_reais`, `forma_pagamento`, `status` (enum: `pendente_admin`, `em_processamento`, `estornado`, `erro`), `erro_detalhe`, `processado_por`, `processado_em`, `criado_em`, `atualizado_em`. Índice real ordena fila por `(status, criado_em)` para `status = 'pendente_admin'`. [Source: docs/architecture/03-data-models.md#6.1 reembolsos_pendentes]
- **`pedidos`**: campos relevantes a esta story — `numero` (nº humano, ex. #2048), `status` (enum completo listado na Task 4), `cliente_id`, `estabelecimento_id`, `hub_id`, `motivo_cancelamento`, `subtotal_produtos_reais`, `taxa_deslocamento_reais`, `taxa_keepit_reais` (12% do subtotal), `total_pago_reais`, timestamps (`criado_em`, `pago_em`, `aceito_em`, `saiu_hub_em`, `cliente_chegou_em`, `lojista_chegou_em`, `entregue_em`, `cancelado_em`). `entregue_em` é o gatilho real da carteira do lojista (D+7) — relevante para o Dashboard Financeiro (GMV/receita só de pedidos `entregue`). [Source: docs/architecture/03-data-models.md#5.1 pedidos]
- **`clientes`**: `bloqueado` (boolean, default false), `motivo_bloqueio` (text). Índice parcial `idx_clientes_bloqueado` só sobre `bloqueado = true`. [Source: docs/architecture/03-data-models.md#1.1 clientes]
- **`estabelecimentos`**: `status` (enum: `em_analise`, `ativo`, `rejeitado`, `suspenso`), `motivo_rejeicao`, `motivo_suspensao`, `suspenso_em`, `pausado_manualmente`. [Source: docs/architecture/03-data-models.md#1.4 estabelecimentos]
- **`estabelecimentos_falhas`**: `estabelecimento_id`, `pedido_id` (nullable), `tipo` (enum: `lojista_nao_apareceu`, `atraso_grave`, `chargeback`, `reclamacao_admin`), `detalhes`, `criado_em`. Esta é a tabela-fonte da "Vista de qualidade do lojista" (Task 9). [Source: docs/architecture/03-data-models.md#1.6 estabelecimentos_falhas]
- **`admin_users`**: flag simples de quem é admin (`id`, `nome`, `criado_em`) — relevante apenas como referência de "quem processou" (`processado_por` em reembolsos); não há tela de gestão de admins nesta story. [Source: docs/architecture/03-data-models.md#1.7 admin_users]
