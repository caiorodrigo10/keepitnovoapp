## Story

**As a** cliente,
**I want** ao submeter o cadastro, uma conta ser criada em Supabase Auth e uma linha em `clientes`,
**so that** minha conta exista e permita login futuro.

[Source: docs/prd/epics/2-auth-cliente.md, Story 2.3]

## Acceptance Criteria

1. Migration cria tabela `clientes (id uuid PK referencing auth.users, nome text, telefone text nullable, cpf text nullable, criado_em timestamptz default now())`. **Sem coluna `telefone_confirmado`** — telefone não é verificado no MVP (decisão 10.4).
2. RLS ativada: cliente só pode ler/atualizar sua própria linha.
3. Trigger insere linha em `clientes` automaticamente ao criar user em `auth.users` (com metadata nome + telefone, sendo telefone possivelmente nulo).
4. Erro de e-mail já existente é mostrado claramente na tela.
5. Sucesso navega direto para a home do cliente (home vazia; Épico 5 preenche depois). Não há etapa intermediária de confirmação de telefone nem de e-mail — respaldado pela decisão técnica provisória 10.5 (`Confirm email` OFF), não mais por default implícito. Se a 10.5 for revertida para ON, esta AC ganha uma tela "confirme seu e-mail" antes da home.

[Source: docs/prd/epics/2-auth-cliente.md, Story 2.3 — ACs 1-5, texto literal]

## ⚠️ Divergência crítica épico vs arquitetura — reconciliada, NÃO é conflito de conteúdo

**Fontes comparadas:**
- Épico: `docs/prd/epics/2-auth-cliente.md`, AC1 — `clientes (id uuid PK referencing auth.users, nome text, telefone text nullable, cpf text nullable, criado_em timestamptz default now())`.
- Arquitetura: `docs/architecture/03-data-models.md` §1.1 — DDL completo com 9 colunas: `id, nome, telefone, cpf, expo_push_token, notificacoes_ativas, bloqueado, motivo_bloqueio, hub_padrao_id, criado_em, atualizado_em, excluido_em` (contei 12, o AC1 do épico cita 5).

**Veredito, verificado linha a linha:** **não há conflito de conteúdo.** A própria `03-data-models.md` §1.1 já traz uma nota explícita de reconciliação (linha 82) dizendo, literalmente: *"Este bloco é a fonte de verdade do DDL e bate com a Story 2.3 do Épico 2 [...], que define o subconjunto mínimo criado na migration do Épico 2 (`id`, `nome`, `telefone` nullable, `cpf` nullable, `criado_em`). As demais colunas abaixo pertencem a épicos posteriores (push, bloqueio, soft delete) e entram por migrations incrementais."*

Ou seja: o épico **resumiu** (5 colunas mínimas para o Épico 2 funcionar), a arquitetura **detalhou** (schema final da tabela, a ser atingido por migrations incrementais ao longo dos épicos 2, 5 e além). É exatamente o caso "o épico resumiu, a arquitetura é o documento especialista" — sigo a arquitetura, mas **apenas para o subconjunto que a própria arquitetura atribui a esta story**.

**Delta exato aplicado nesta migration (Task 1):**

| Coluna | Nesta migration (Story 2.3)? | Fonte / motivo |
|---|---|---|
| `id uuid PK REFERENCES auth.users(id) ON DELETE CASCADE` | ✅ Sim | Épico AC1 + arquitetura §1.1 |
| `nome text NOT NULL` | ✅ Sim | Épico AC1 + arquitetura §1.1 |
| `telefone text` (nullable) | ✅ Sim | Épico AC1 + arquitetura §1.1 + decisão 10.4 |
| `cpf text` (nullable) | ✅ Sim | Épico AC1 + arquitetura §1.1 |
| `criado_em timestamptz NOT NULL DEFAULT NOW()` | ✅ Sim | Épico AC1 + arquitetura §1.1 |
| `expo_push_token text` | ❌ Não | Arquitetura atribui a push (Story 2.11) — fora do escopo desta AC |
| `notificacoes_ativas boolean DEFAULT true` | ❌ Não | Arquitetura atribui a Story 2.9/2.11 (toggle de notificações) |
| `bloqueado boolean DEFAULT false` | ❌ Não | Arquitetura atribui a moderação/admin (Épico 3/9), sem story deste épico usando |
| `motivo_bloqueio text` | ❌ Não | Idem |
| `hub_padrao_id uuid` | ❌ Não | Arquitetura marca como "reservado para v2 ('hub favorito'); no MVP fica NULL" — nem entra agora |
| `atualizado_em timestamptz` + trigger `set_atualizado_em` | ❌ Não nesta migration | Só faz sentido quando a tabela ganha colunas mutáveis por UPDATE de rotina (perfil, Story 2.8) — **registrado como pendência abaixo**, não decidido sozinho |
| `excluido_em timestamptz` (soft delete) | ❌ Não | Arquitetura atribui a exclusão de conta (Story 2.9, WhatsApp) — fora do escopo desta AC |

**Índices:** `idx_clientes_telefone`, `idx_clientes_cpf` do §1.1 **não entram** nesta migration — servem a `bloqueado`/`telefone` para busca administrativa (Épico 3/9), sem consumidor nesta story. Adicioná-los agora seria antecipar índice sem query que o use, o que a própria arquitetura não pede para esta story.

**⚠️ Pendência não resolvida sozinha (registrar, não decidir):** a AC2 do épico (RLS: cliente só lê/atualiza a própria linha) versus a policy `cliente_atualiza_proprio` de `05-security.md` §3.1, que faz `WITH CHECK (... AND bloqueado = (SELECT bloqueado FROM clientes WHERE id = auth.uid()))` — **essa policy referencia a coluna `bloqueado`, que por este delta NÃO existe na migration desta story.** Se a Task 3 (@data-engineer) aplicar a policy literalmente como está em `05-security.md`, a migration **quebra** (coluna inexistente). Duas saídas possíveis, e a escolha entre elas é técnica, não de negócio — mas ainda assim **não decidida por esta story**: (a) `@data-engineer` adapta a policy desta migration para a tabela mínima (sem a cláusula `bloqueado`) e revisita quando `bloqueado` for adicionado por migration futura; (b) adiantar a coluna `bloqueado` nesta migration para casar com a RLS documentada. **Task 3 abaixo instrui explicitamente a opção (a)** como a que preserva o delta acima sem inflar escopo — mas isso é uma decisão técnica de sequenciamento tomada nesta story de forma explícita e documentada, não uma omissão. Se o @data-engineer discordar do sequenciamento ao implementar, deve levar ao @architect antes de aplicar.

## Dev Notes

### [PO] Contrato normativo de `raw_user_meta_data` — FIXADO POR ESTA STORY

O @sm registrou os nomes das chaves em dois lugares (Task 3 e Task 6) e classificou a sincronização como algo "a combinar durante a implementação". **Isso é lacuna, e está fechada aqui.** Um contrato de interface entre dois executores não pode depender de dois agentes lembrarem de conversar: se @data-engineer escrever `->>'nome'` e @dev enviar `{ nomeCompleto }`, o `COALESCE(..., '')` do trigger grava `nome = ''` **sem erro, sem exceção, sem log** — o cliente entra no banco sem nome e ninguém percebe até alguém abrir o painel admin. Falha silenciosa é a pior categoria.

**Este bloco é a fonte de verdade única. Ambos os executores leem daqui, ninguém "combina" nada.**

| Chave em `raw_user_meta_data` | Tipo | Origem (@dev, Task 6) | Consumo (@data-engineer, Task 3) |
|---|---|---|---|
| `nome` | `string` não vazia | `options.data.nome` ← `nome.trim()` do form | `NEW.raw_user_meta_data->>'nome'` → `clientes.nome` |
| `telefone` | `string` ou ausente | `options.data.telefone` ← `telefone.trim() \|\| null` | `NULLIF(NEW.raw_user_meta_data->>'telefone', '')` → `clientes.telefone` |

Chaves em **minúsculas, sem acento, sem camelCase**. Nenhuma outra chave é enviada nesta story. Divergir deste bloco = quebrar a AC3.

**Verificação obrigatória (não é opcional, não é "confiar na leitura"):** Task 4b assere via `SELECT` real que `clientes.nome` chegou igual ao nome enviado. É o único ponto do fluxo onde a divergência de chaves fica visível.
