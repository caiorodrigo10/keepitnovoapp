## Story

**As a** dev solo,
**I want** o diretório `packages/core-data/src/supabase/` com o esqueleto da implementação Supabase de cada port definida no Épico 0 (e estendida na Story 1.10), religando `createDataClient({ source: 'supabase' })` para essa implementação,
**so that** os épicos 2–9 tenham um alvo claro e já religado para substituir mock por dado real, port por port, sem precisar reabrir a factory ou o contrato de tipos a cada épico.

## Acceptance Criteria

1. `packages/core-data/src/supabase/` contém um arquivo por port — **8 arquivos**: `auth.supabase.ts`, `hub.supabase.ts`, `store.supabase.ts`, `product.supabase.ts`, `order.supabase.ts`, `wallet.supabase.ts`, `admin.supabase.ts`, `analytics.supabase.ts` — cada um implementando a MESMA interface já definida em `packages/core-data/src/ports/*.port.ts` (Story 0.2 + extensão da Story 1.10), usando o `supabase-client` tipado (Story 1.4: `createClient()`/`createServiceRoleClient()` de `@keepit/supabase-client`).
2. No esqueleto, cada método lança `NotImplementedError` com mensagem padronizada identificando port + método + épico responsável pela implementação real — o preenchimento real é responsabilidade dos épicos 2–9. Métodos triviais que já dão para implementar sem inventar schema (ex.: um `SELECT` simples contra uma tabela que hoje só tem o canário) ficam a critério do @dev; nenhuma tabela de domínio real é criada nesta story.
3. `createDataClient({ source: 'supabase' })` resolve para essa implementação (a factory em `packages/core-data/src/index.ts` para de lançar erro para `source: 'supabase'` e passa a instanciar os 8 adaptadores Supabase); `source: 'mock'` continua resolvendo para o mock do Épico 0/1.10, sem nenhuma mudança de comportamento.
4. A flag de fonte (`DATA_SOURCE`) é lida de env; default documentado (`'mock'` quando ausente ou vazia). Mecanismo exato de leitura (dentro da própria factory vs. no bootstrap de cada app) é decisão do @dev, documentada nas Dev Notes.
5. `pnpm turbo run typecheck` e `pnpm turbo run test` passam sem regressão em nenhum dos 9 workspaces existentes; nenhuma tela de `apps/cliente`, `apps/lojista` ou `apps/admin` é tocada (todos os apps continuam chamando `getDataClient()` sem argumento, portanto continuam em `'mock'` — a troca de fonte não exige mudança em nenhuma tela).

### Escopo desta story (contexto obrigatório)

- Esta é a **story de wiring**, não de implementação de negócio. Nenhuma tabela de domínio real (`clientes`, `hubs`, `estabelecimentos`, `produtos`, `pedidos`, `saques`, `reembolsos_pendentes`) existe hoje em `apps/supabase/migrations/` — só `_canary` (Story 1.4).   - Nenhuma lógica de negócio real (cálculo de taxa, matriz de cancelamento, PIN real, etc.) — isso é dos épicos 2–9, cada um plugando sua port quando a tabela correspondente nascer.

Trocar para `'supabase'` hoje resultaria em `NotImplementedError` em qualquer chamada real — isso é esperado e correto até o épico correspondente preencher o método.

Baseado na lista real de épicos em `docs/prd/05-epics.md` (verificada nesta sessão: Épico 2 Auth Cliente, Épico 3 Auth Lojista + Aprovação Admin, Épico 4 Cadastros Base — Hubs & Catálogo, Épico 5 Descoberta & Busca, Épico 6 Pedido & PIN, Épico 7 Pagamento & Carteira, Épico 8 Painel Admin — Operação, Épico 9 Publicação). O `epicHint` passado ao `NotImplementedError` de cada método deve refletir o épico correto daquele método específico (não um único hint fixo para o arquivo inteiro) — usar a tabela acima como guia. Isso é só uma string de mensagem de erro (não afeta o contrato/tipo), então um ajuste incorreto não bloqueia a story, mas deve ser o mais preciso possível para orientar os épicos futuros.
