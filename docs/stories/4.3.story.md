## Story

**As a** lojista ativo,
**I want** ver todos meus produtos cadastrados com foto, nome, preço e estado
(ativo/pausado), lendo dados reais do Supabase,
**so that** eu tenha visão completa e confiável do meu catálogo.

## Acceptance Criteria

1. A rota "Catálogo" já existente (`GerenciarCatalogo.tsx`, Story 0.9) lista,
   com dados reais quando `DATA_SOURCE=supabase`, os produtos do
   estabelecimento do lojista autenticado — cards com foto pequena, nome,
   preço e estoque de exibição (`estoqueDisplay`, valor derivado
   client-side, não uma coluna real — "Não há tabela de estoque",
   `docs/architecture/03-data-models.md#3.1`). [Fonte:
   `docs/prd/epics/4-cadastros-base.md` Story 4.3 AC1]

2. Tabs/filtros "Ativos"/"Pausados" (e "Todos", já existente) continuam
   funcionando sobre a lista real — "Pausados" traz produtos com `ativo =
   false` (nunca os com `excluido_em` preenchido), usando
   `ProductPort.list(estabelecimentoId, { incluirInativos: true })`. [Fonte:
   `docs/prd/epics/4-cadastros-base.md` Story 4.3 AC2]

3. Botão flutuante "+ Novo" (já existente) continua levando a
   `CadastrarProduto` (Story 4.4, sem mudança nesta Story). [Fonte:
   `docs/prd/epics/4-cadastros-base.md` Story 4.3 AC3]

4. Cada card mantém seu menu (editar via toque, pausar/reativar via toggle
   inline, excluir dentro de `EditarProduto`) — sem mudança de UI; o efeito
   passa a ser real quando as Stories 4.5/4.6 ligarem `update`/`pause`/
   `delete` a dados reais (fora do escopo desta Story, que é só leitura).
   [Fonte: `docs/prd/epics/4-cadastros-base.md` Story 4.3 AC4]

5. Estados de loading/vazio/erro (já existentes na tela) são preservados e
   continuam funcionando com dados reais — falha de rede/RLS exibe erro
   real, nunca uma lista vazia disfarçada de sucesso. Um lojista sem nenhum
   produto cadastrado ainda vê o estado vazio real ("Nenhum produto
   cadastrado ainda."), não um erro. [Fonte: `docs/stories/README.md`
   "Definition of Done adicional"]

6. RLS garante que o lojista só vê produtos do PRÓPRIO estabelecimento — uma
   tentativa (mesmo que hipotética, via client manipulado) de listar
   produtos de outro `estabelecimento_id` não retorna dados de outro
   lojista; a barreira é o Postgres (`lojista_gerencia_produtos`), não um
   filtro client-side. [Fonte: `docs/architecture/05-security.md §3.9`]

## Dev Notes

### Contexto e limites

- A tela `GerenciarCatalogo.tsx`, o `ProductCatalogContext.tsx` e o contrato
  `ProductPort` já existem inteiros desde as Stories 0.9/1.10 — esta Story
  **não redesenha nada**, apenas liga a leitura a dados reais. [Source:
  `apps/lojista/src/screens/catalogo/GerenciarCatalogo.tsx`,
  `apps/lojista/src/screens/catalogo/ProductCatalogContext.tsx`]
- `ProductPort.list(estabelecimentoId, { incluirInativos })` já é o contrato
  usado pela tela — nenhuma mudança de assinatura é esperada, só a
  implementação real por trás. [Source:
  `packages/core-data/src/ports/product.port.ts`]
- `product.supabase.ts` é hoje um esqueleto completo com todos os métodos
  (`list`, `getById`, `create`, `update`, `pause`, `delete`) lançando
  `NotImplementedError(..., 'Épico 4')` — esta Story implementa só `list`;
  `create`/`update`/`pause`/`delete` ficam para as Stories 4.4/4.5/4.6.
  [Source: `packages/core-data/src/supabase/product.supabase.ts`]
- `estoqueDisplay` é um valor de EXIBIÇÃO derivado client-side
  (`estoque.ts#estoqueDisplayFromId`, determinístico a partir do `id`) — não
  existe coluna de estoque no schema real (`docs/architecture/03-data-models.md#3.1`,
  "Não há tabela de estoque. Decisão de negócio: lojista administra estoque
  fora do app."). Esta Story não muda esse comportamento. [Source:
  `apps/lojista/src/screens/catalogo/estoque.ts`,
  `apps/lojista/src/screens/catalogo/types.ts`]
- **Sequenciamento prático:** sem nenhum produto criado ainda (Story 4.4 é
  quem cria dados reais pela primeira vez), o resultado real desta Story
  isolada é uma lista vazia genuína no `keepit-dev` até que 4.4 rode — não é
  um bug desta Story, é a ordem natural leitura-antes-de-escrita quando as
  duas são Stories separadas (diferente do padrão CRUD único da Story 4.1).
  Recomenda-se implementar/validar 4.3 e 4.4 em sequência próxima.
