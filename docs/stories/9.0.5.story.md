um gate novo.

**Excluído:** qualquer reintrodução de auto-avanço de pedido sem o gate de
dev (fora de escopo — ver Riscos, mitigação futura possível, não desta

## Dev Notes

### Achado principal desta story: o gate já existe

Leitura de `apps/cliente/src/components/discovery/DevStateToggle.tsx` (linha
39: `if (!__DEV__) { return null; }`) e
`apps/cliente/src/components/pedidos/OrderStatusDevAdvancer.tsx` (linha 21:
mesmo padrão) confirma que **ambos os componentes já são `__DEV__`-only desde
que foram criados** (Story 0.5 para `DevStateToggle`, Story 0.7/1.10 para
`OrderStatusDevAdvancer` — comentários JSDoc de cada arquivo citam essas
stories). O mesmo padrão é usado em
`apps/cliente/src/screens/perfil/Configuracoes.tsx` linha 63, exatamente como
o épico cita.

`__DEV__` é `true` apenas quando o JS bundle roda em modo desenvolvimento
(Metro dev server ou `expo-dev-client`) e `false` em qualquer bundle de
release — incluindo builds `eas build` **sem** `developmentClient: true`.
Como nenhum dos dois apps instala `expo-dev-client` (grep confirmado,
Task 2) e o profile `pilot` da Story 9.0.2 não é um profile de
desenvolvimento, o build do piloto já produz `__DEV__ === false` — os dois
componentes já não renderizam, sem nenhuma mudança de código adicional.

### O que esta story realmente entrega

Diferente de outras stories da Fase 0, o valor desta story é
majoritariamente **verificação e documentação da garantia**, não escrita de
código novo. Isso é esperado e correto — a Task 4 já antecipa que o
`git diff` pode ficar vazio. Se a implementação confirmar os achados acima
sem gerar nenhuma mudança de arquivo, isso **não é uma story "vazia"**: é uma
story que evita que alguém, no futuro, presuma incorretamente que falta
trabalho aqui e introduza um segundo mecanismo de gate (ex.: uma env var
`HIDE_DEV_CONTROLS`) redundante com o `__DEV__` já correto.
