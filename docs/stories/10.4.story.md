  não renderiza.
- Compatibilidade: mudança de UI (1 tela) + fixture (1 linha determinística
  em vez de `Math.random()`). Não altera nenhuma port, nenhum contrato,
  nenhuma lógica de `confirmPin`.

## Acceptance Criteria

1. Em build mock, na tela `DigitarPin` de um pedido com `status === 'no_hub'`,
   aparece uma dica discreta mostrando o PIN esperado
   (`pedido.pin_texto`) — próxima à instrução existente ("Peça o código de
   4 dígitos ao cliente"), sem alterar o texto/estilo dessa instrução.
2. Digitar o PIN mostrado na dica e confirmar completa o fluxo de ponta a
   ponta: `onConfirmarEntrega` → `confirmPin` retorna `correto: true` →
   navega para `ConfirmarRetirada` (comportamento já existente, não
   modificado).
3. Em build supabase (`isSupabaseDataSource()` retorna `true`), a dica
   **não** é renderizada — o bloco condicional inteiro fica ausente da
   árvore de componentes (não é só `display:none`/opacidade 0).
4. Nenhuma fixture de pedido usa `Math.random()` para gerar `pin_texto` —
   o `pin_texto` default em `montarPedido` (`fixtures/pedidos.ts`, hoje
   linha ~40) passa a ser determinístico entre execuções/boots (mesmo valor
   sempre, para o mesmo pedido). Os PINs já fixos explicitamente por pedido
   (ex.: `'4567'` no `no_hub`, `'4821'`, `'7734'`, etc.) permanecem
   inalterados.
5. A lógica de `confirmPin` (`apps/lojista/src/screens/pedidos/OrdersContext.tsx`
   ou onde estiver implementada — tentativas, bloqueio temporário,
   mensagens de erro) permanece **byte-a-byte inalterada**; só a UI de
   `DigitarPin.tsx` ganha o bloco condicional novo.
6. `pnpm --filter @keepit/core-data test` continua 100% verde após a troca
   do `Math.random()` — se algum teste dependia de um `pin_texto`
   não-determinístico (pouco provável, mas verificar), ajustar e
   documentar.

## Dev Notes

### Diagnóstico (por que a demo não consegue mostrar o PIN hoje)

- `DigitarPin.tsx` (`apps/lojista/src/screens/pedidos/DigitarPin.tsx`)
  obtém o `pedido` via `getById(pedidoId)` (`useOrdersContext`) e compara o
  PIN digitado dentro de `confirmPin`; a instrução na tela diz "Peça o
  código de 4 dígitos ao cliente". Numa demo com só o app do Lojista, o
  apresentador não tem de onde tirar esse código — o app do Cliente (que
  mostraria o PIN) não está sendo demonstrado.
- O dado já existe: `Pedido.pin_texto` está no tipo
  (`packages/core-data/src/ports/order.port.ts`, comentário "expõe apenas
  `pin_texto`, exibição ao cliente; `pin_hash` NUNCA") e está **populado em
  todas as fixtures de pedido**. `pedido.pin_texto` é acessível dentro de
  `DigitarPin` (já lido via `getById`) **sem mudar nenhum contrato**.
- **Gap embutido:** `packages/core-data/src/mock/fixtures/pedidos.ts`,
  dentro de `montarPedido` (linha ~40), o `pin_texto` **default** (usado
  pelos pedidos que não sobrescrevem esse campo via `...input`) é gerado
  com `String(1000 + Math.floor(Math.random() * 9000))` — não-determinístico
  entre boots do app. A maioria dos pedidos já sobrescreve `pin_texto`
  explicitamente (9 ocorrências confirmadas: `'4821'`, `'7734'`, `'4567'`
  — este é o pedido `no_hub` já citado no design —, `'1123'`, `'2244'`,
  `'3355'`, `'4466'`, `'5577'`, `'9182'`), então o impacto prático do
  `Math.random()` está limitado aos pedidos que não definem `pin_texto`
  explicitamente. Ainda assim, fixar o default é parte do escopo (AC4).

### Trecho relevante de `fixtures/pedidos.ts`

```ts
function montarPedido(input: PedidoFixtureInput): Pedido {
  // ...
  return {
    pin_texto: String(1000 + Math.floor(Math.random() * 9000)), // ← trocar por valor determinístico
    tentativas_pin: 0,
    pin_bloqueado_ate: null,
    // ...
    ...input, // pedidos que passam `pin_texto` explicitamente sobrescrevem o default acima
  };
}
```

### Trecho relevante de `DigitarPin.tsx` (onde inserir a dica)

```tsx
<Text style={[styles.instrucao, { color: darkColors.text.tertiary }]}>
  Peça o código de 4 dígitos ao cliente
</Text>
{/* AC1/AC3 — inserir aqui o bloco condicional gated por !isSupabaseDataSource() */}
```

O `pedido` já está disponível no escopo do componente (`const pedido =
getById(pedidoId)`), então `pedido.pin_texto` é diretamente acessível — sem
nenhuma nova chamada de dados.

### `isSupabaseDataSource()` — padrão de gating já estabelecido

`apps/lojista/src/lib/dataSource.ts`:

```ts
export function isSupabaseDataSource(): boolean {
  return process.env.EXPO_PUBLIC_DATA_SOURCE?.trim() === 'supabase';
}
```

Mesmo helper já usado por outras telas do app Lojista para diferenciar
comportamento mock vs. produção (ver JSDoc do próprio arquivo, que cita
`PerfilPublico.tsx`/`Configuracoes.tsx` como precedentes de uso
screen-level). Usar exatamente este import — não recriar a checagem da env
var localmente em `DigitarPin.tsx`.

### Nota de segurança (fora de escopo, só registro)

O design técnico confirma que, no mock, expor `pedido.pin_texto` no app
Lojista é seguro (dado fake). Fica registrado — **fora do escopo desta
story** — que em produção o app do Lojista **não deveria** receber
`pin_texto` no `SELECT` do adapter Supabase de pedidos (é o segredo que o
app Cliente exibe ao usuário para retirada). Auditar isso é carry-forward
de segurança para uma frente separada (Épico 6+/segurança), não faz parte
do modo demo.
