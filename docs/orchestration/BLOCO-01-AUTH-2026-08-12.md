## 2. Pipeline por story (executa sem parar)

Para cada story, em ordem:

```text
@sm  materializa/atualiza a Story (cabeçalho do piloto + Data Mode)
 → @po valida ACs e marca Ready
 → @data-engineer aplica migration/RLS em keepit-dev via MCP  [só se toca DB]
      → get_advisors(security) após a DDL — 0 lints obrigatório
 → @dev implementa (Sonnet) — DATA_SOURCE flag preservada, mock intacto
      → @dev roda testes direcionados + `pnpm qa`
 → @qa (Opus) emite PASS / CONCERNS / FAIL
      → FAIL: volta ao @dev (máx. 3 ciclos)
 → integra localmente após PASS ou CONCERNS-sem-critical/high
 → @aiox-master atualiza estado e segue para a próxima story
```

**Regras herdadas:** executor ≠ gate; nenhum sucesso fictício; QA nunca é
pulada; migrations forward-only; `DATA_SOURCE=mock` continua sendo o default
seguro e as fixtures não são apagadas.

**Concorrência:** **sequencial** neste bloco — as stories de Cliente
compartilham a mesma superfície de UI (Perfil/auth/navigator) e as de Lojista
compartilham o cadastro; paralelizar sobrescreveria arquivos.

**Migrations previstas neste bloco (via MCP `apply_migration`):**
- Cliente: nenhuma nova estrutura obrigatória (a `clientes` já existe); ajustes
  incrementais só se a AC exigir coluna nova.
- Lojista (3.x): `estabelecimentos` (subconjunto mínimo enxuto — sem geo NOT NULL,
  sem `asaas_api_key_encrypted`, `asaas_wallet_id` NULL) + RLS por ownership +
